# API 与 Webhook 对接实战指南

> 目标：理解 API、Webhook、对接流程和常见问题，并能够处理 PC-LP 真实联调。

## 1. API 是什么

API 是“主动请求”。一方调用另一方的地址，并等待返回结果。

```text
LP ──请求──> PC
LP <─响应── PC
```

例如 LP 查询 PC 的号码：

```http
GET /api/projects/project_001/numbers?status=available
Authorization: Bearer <token>
```

PC 返回：

```json
{
  "items": [
    {
      "numberId": "number_001",
      "phoneNumber": "+12025550100",
      "status": "available"
    }
  ]
}
```

### API 对接需要明确的内容

每个 API 都要明确：

- 请求地址和 HTTP 方法：`GET`、`POST`、`PUT`、`DELETE`；
- 请求头：鉴权、内容类型、签名；
- 请求参数：路径参数、Query 参数、Body；
- 成功响应格式；
- 失败响应格式；
- 状态码含义；
- 超时、重试和幂等规则。

## 2. HTTP 请求的基本结构

```http
POST /api/orders
Authorization: Bearer token
Content-Type: application/json
Idempotency-Key: order_001

{
  "projectId": "project_001",
  "numberId": "number_001"
}
```

### 常见方法

| 方法 | 用途 | 是否应改变数据 |
|---|---|---|
| `GET` | 查询 | 否 |
| `POST` | 创建/执行动作 | 通常是 |
| `PUT/PATCH` | 更新 | 是 |
| `DELETE` | 删除/释放 | 是 |

### 常见状态码

| 状态码 | 含义 |
|---|---|
| `200` | 查询或操作成功 |
| `201` | 创建成功 |
| `400` | 参数错误 |
| `401` | 未认证 |
| `403` | 无权限 |
| `404` | 资源不存在 |
| `409` | 状态冲突或重复操作 |
| `429` | 请求过多 |
| `500/502/503` | 对方或网关暂时异常 |

## 3. Webhook 是什么

Webhook 是“被动接收通知”。一方发生事件后，主动调用另一方提供的 URL。

```text
PC 发生短信事件
    ↓
PC ──POST──> LP Webhook
LP 返回 200/错误码
```

Webhook 不是让 LP 定时查询，而是事件推送。

LP 当前接收入口：

```http
POST /api/webhooks/pingcode
```

示例：

```json
{
  "eventId": "evt_001",
  "event": "sms.received",
  "occurredAt": "2026-01-01T12:00:00Z",
  "data": {
    "projectId": "project_001",
    "numberId": "number_001",
    "phoneNumber": "+12025550100",
    "messageId": "msg_001",
    "from": "+8613800138000",
    "content": "Your code is 123456"
  }
}
```

## 4. API 和 Webhook 的区别

| 项目 | API | Webhook |
|---|---|---|
| 谁发起 | LP 主动发起 | PC 主动发起 |
| 触发方式 | LP 需要时调用 | PC 发生事件时调用 |
| 典型用途 | 查询项目、号码、短信 | 推送短信、号码状态变化 |
| 是否需要响应 | 需要 | 需要返回接收结果 |
| 主要风险 | 超时、限流、权限 | 重复、丢失、乱序、重试 |

实际系统通常两者一起使用：

- API：首次同步、查询、补偿；
- Webhook：实时通知变化。

## 5. 本项目推荐的对接关系

```text
┌────────┐       查询项目/号码       ┌────────┐
│   LP   │ ───────────────────────> │   PC   │
│        │ <─────────────────────── │        │
└────────┘       返回数据           └────────┘
    ▲                                  │
    │                                  │ 短信/号码状态 Webhook
    └──────────────────────────────────┘
```

### LP 主动调用 PC

```http
GET /api/projects
GET /api/projects/{projectId}/numbers
GET /api/messages/{messageId}
```

### PC 主动调用 LP

```http
POST /api/webhooks/pingcode
```

## 6. 一次完整对接应该怎么做

### 第一步：确定业务边界

先确认：

- PC 是批量提供号码，还是每次销售都申请；
- `projectId` 是否代表平台项目；
- `numberId` 是否稳定唯一；
- 一个号码能否同时支持多个项目；
- 号码过期、释放、禁用时如何通知。

### 第二步：拿到接口资料

至少需要：

- API 地址；
- 鉴权方式；
- 请求和响应样例；
- 错误码；
- 签名算法；
- 重试规则；
- 测试环境和测试账号；
- 测试项目、测试号码和测试短信。

### 第三步：先做只读联调

优先验证：

```text
获取项目 → 获取号码 → 查看号码状态 → 查询短信
```

不要一开始就做购买、扣款、分配等不可逆操作。

### 第四步：接入 Webhook

验证：

1. PC 能访问 LP 的 Webhook URL；
2. 签名能校验成功；
3. 请求字段完整；
4. LP 能根据 `projectId + numberId` 找到归属；
5. 重复发送不会产生重复短信；
6. LP 返回 `200` 后 PC 不再重复发送。

### 第五步：做异常测试

必须测试：

- 错误签名；
- 缺少字段；
- 重复事件；
- 号码不存在；
- Webhook 暂时返回 500；
- PC 重试；
- 短信正文为空；
- 号码已经过期；
- 项目状态已关闭。

## 7. Webhook 必须处理的边界情况

### 7.1 重复事件

PC 可能因为没有及时收到响应而重复发送同一个事件。

处理方式：

- 使用 `eventId` 或 `messageId` 做唯一键；
- 已处理过的事件直接返回 `200`；
- 不能重复创建短信或重复发放权益。

### 7.2 乱序事件

网络不能保证事件顺序。例如先收到“释放号码”，后收到“短信到达”。

处理方式：

- 保存事件时间；
- 按业务状态判断；
- 必要时保留原始事件等待补偿；
- 不要只按请求到达顺序覆盖数据。

### 7.3 Webhook 丢失

Webhook 可能因网络、部署或超时丢失。

处理方式：

- PC 必须支持失败重试；
- PC 最好提供短信查询接口；
- LP 定期按时间范围或 `messageId` 补偿；
- 原始事件需要记录日志。

### 7.4 签名错误

签名错误时：

- 不处理业务数据；
- 返回 `401` 或 `403`；
- 记录请求时间、事件 ID 和错误原因；
- 不要把完整敏感短信正文写入普通日志。

### 7.5 未知项目或号码

如果 `projectId + numberId` 在 LP 查不到：

- 保存原始事件；
- 不展示给任何客户；
- 不要猜测归属；
- 通过项目/号码同步后再补偿处理。

### 7.6 号码回收后收到旧短信

旧号码的短信不能直接展示给新客户。

LP 必须根据短信发生时间和号码分配有效期判断归属。

### 7.7 PC 返回超时

如果 LP 已经成功入库，但响应丢失，PC 可能重试。

因此：

> 入库必须先幂等，再返回成功；不能用“是否返回成功”判断是否已经处理过。

## 8. 真实业务中最容易混淆的概念

### 项目不是客户

`projectId` 通常表示 PC 的平台/业务项目，例如 Telegram 项目；它不一定是 LP 的最终客户。

### 号码不是订单

同一个号码可能在不同时间属于不同客户。订单、权益、号码和短信必须分开记录。

### Webhook 成功不等于业务成功

HTTP `200` 只表示 LP 已接收事件，不代表短信一定已经展示给用户。LP 内部还需要完成：

```text
校验 → 幂等 → 归属 → 入库 → 展示
```

### 可用不等于已分配

号码状态至少要区分：

```text
available  可销售
assigned   已分配
expired    已过期
released   已释放
disabled   已禁用
```

## 9. 对接出现问题时怎么处理

### 先判断问题在哪一层

```text
PC 是否发出了请求？
  ↓
请求是否到达 LP？
  ↓
签名是否通过？
  ↓
参数是否完整？
  ↓
项目/号码是否存在？
  ↓
是否正确归属客户？
  ↓
是否入库和展示？
```

### 常见问题排查表

| 现象 | 优先检查 |
|---|---|
| LP 没收到 Webhook | URL、网络、防火墙、PC 发送日志 |
| 返回 401/403 | 密钥、签名算法、时间戳、请求体是否一致 |
| 返回 400 | 字段名、类型、必填字段、时间格式 |
| 返回 404 | `projectId`、`numberId` 是否已同步 |
| 短信重复 | `eventId/messageId` 是否做唯一约束 |
| 短信给错客户 | 项目、号码、分配有效期和平台映射 |
| PC 一直重试 | LP 是否返回 200、响应是否超时 |
| 号码列表为空 | 项目 ID、状态筛选、分页和权限 |
| 短信没有正文 | Webhook 是否携带 `content`，补偿 API 是否可用 |
| 号码状态不一致 | 是否有定期同步和状态变化事件 |

### 每次联调都要记录

```text
请求时间
请求 URL
HTTP 状态码
eventId / messageId
projectId / numberId
请求摘要
响应摘要
错误日志
```

不要在普通日志中记录完整 Token、签名密钥和不必要的短信正文。

## 10. 需要向 PC 负责人提出的问题

1. 项目列表和号码列表 API 是什么？
2. 是否支持分页、状态筛选和增量同步？
3. `projectId`、`numberId`、`messageId` 是否稳定唯一？
4. Webhook 是否携带完整短信正文？
5. Webhook 是否签名？签名原文是什么？
6. 失败后多久重试，最多重试几次？
7. 是否支持查询某个 `messageId` 进行补偿？
8. 号码过期、释放、禁用如何通知？
9. 一个号码能否同时属于多个项目？
10. 是批量供号还是逐单申请？
11. 是否提供测试环境和测试数据？
12. 出问题时双方通过什么日志或事件 ID 对查？

## 11. 当前 LP 的开发顺序

### 第一阶段：接口确认

- 完成 PC API 文档确认；
- 拿到真实请求和响应样例；
- 确认批量供号或逐单申请；
- 确认签名和重试。

### 第二阶段：只读同步

- 接入项目列表；
- 接入号码列表；
- 保存号码状态和有效期；
- 增加定期同步和对账。

### 第三阶段：Webhook

- 接收短信事件；
- 验签；
- 幂等入库；
- 根据项目和号码匹配客户；
- 增加失败重试和补偿。

### 第四阶段：业务闭环

- 号码分配；
- 订单和权益；
- 到期和回收；
- 余额扣款；
- 支付和结算。

## 12. 最终判断标准

只有满足以下条件，才算 PC-LP 基础对接完成：

- 项目和号码可以同步；
- 短信 Webhook 可以验签并接收；
- 短信包含项目和号码归属信息；
- 重复事件不会重复入库；
- 失败事件能够重试或补偿；
- 号码状态变化能够同步；
- 联调双方可以通过 `eventId/messageId` 对查；
- 测试环境完成正常和异常场景验收。

支付、结算、真实采购和生产部署完成后，才算具备正式商业使用条件。
