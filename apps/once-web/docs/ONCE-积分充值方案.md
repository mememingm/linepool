# ONCE 积分充值方案（在线支付）

> 版本：v0.3 · 已批准，开发中 · 2026-11-03。
> 目标：用户在线充值积分，再使用积分租号和续费；资金可追溯，异常可恢复，余额可核对。
> 已明确分工：具体支付渠道由用户同事负责；我方负责积分账户、充值订单、租号续费扣积分、后台及双方业务联调。用户已整体批准以下六条规则，按本方案进入开发；阶段验收及真实上线仍以实际验证结果为准。

## 审核简版（只看这一页即可）

用户使用方式：**充值 → 得到积分 → 租号或续费**。建议第一版采用以下规则：

1. **价格**：套餐按现有价格换算成积分，不借此次改造涨价。
2. **积分**：暂按 1 美元＝100 积分，不过期，不做充值赠送。
3. **额度**：单笔充值 $5–$500，每人每日最多 $500。
4. **退款**：开通/续费明确失败不扣积分；没用掉的实付积分可申请原路退款，补偿积分不退现金。
5. **选号**：充值期间不保号；到账后回来再确认，原号不可用时重新选择。
6. **后台**：建议停止新增线下收费开通/延期；保留免费补偿和历史记录。

**怎么分工**：同事负责渠道收款、查单、退款等具体接入；我方提供统一业务接口和模拟支付，负责收到可信支付结果后正确入账、消费和退分。双方联调时核对订单标识、金额/币种、幂等键和支付/退款状态，确保不重复记账。

**审核通过后的顺序**：先做积分账户、租号/续费扣分和模拟充值；同事渠道接口就绪后共同联调真实支付。主体与渠道资料由同事在接入时落实。

以下为开发参考细则，无需逐项阅读或确认。整体批准时，未提出修改的建议即作为实施基线；技术细节由开发负责。

## 一、目标、现状与第一版范围

### 1.1 当前项目的实际基础

- 已有用户、套餐 `Plan`、租约 `Lease`、消费订单 `Order`、`AppSetting`、管理员审计和部分幂等机制。
- 当前自助租号、续费走演示路径；另有包含 `PENDING / PROCESSING / UNCERTAIN` 的异步履约模拟。真实付费租号、续费能力仍需单独接通并验收。
- 现有 `Payment` 只关联消费 `Order`，尚无积分账户、积分流水、充值单和现金退款单。
- 后台已有填写线下实收金额的开通、延期入口；概览目前按消费订单金额汇总，需要随本方案调整。
- 选号草稿当前只在前端内存中，不能直接承诺跳转支付后仍可恢复。
- 参考 LinePool 的“充值单＋积分流水＋充值规则”思路，不把其他项目的模拟支付当作真实支付已经完成的依据。

### 1.2 第一版做什么

1. 单一交易币种、固定兑换比例，用户通过积分完成自助租号和续费。
2. 积分账户区分可用与冻结；实付积分、补偿积分按来源记录。
3. 充值、入账、消费、解冻、消费退款、现金退款、管理员调整均可追溯。
4. 我方先用模拟渠道验证完整流程，同事负责选定支付渠道的沙箱和生产接入，双方联调。
5. 具备主动查单、未知结果恢复、原路退款、基础对账、限额及异常处理能力。
6. 保留已有租约、订单和线下收款历史，不把演示记录转成真实资产。

### 1.3 第一版暂不做

- 多币种钱包、自动换汇、用户之间转赠、积分提现到任意账户、积分交易。
- 充值赠送、优惠券、会员折扣、自动续费、订阅自动扣款。
- 同时开放“现金直接买套餐”和“积分买套餐”两条自助结算路径。
- 新增线下收款入积分的业务流程；已有历史记录保留，新增入口按第十一节调整。
- 充值期间预留号码、无人值守的管理员代购、复杂财务总账系统。

## 二、需要审核的业务决策

以下建议组成同一套首版规则。修改其中一项时，应同步检查价格、退款、页面与验收；不能只改充值配置。

| 决策 | 本版建议 | 审核与执行边界 |
|---|---|---|
| 服务地区、收款主体、支付渠道 | **由同事负责选型及接入**，按实际主体、用户地区和号码业务准入落实 | 具体渠道待同事确定；我方提供统一业务接口与模拟适配，不依赖选型即可先开发获批的积分业务。真实接入时共同核对币种、金额、可信支付/退款结果及幂等 |
| 交易币种与兑换 | 以现有 USD 标价为工作假设：`1 USD = 100 积分`，即 `1 美分 = 1 积分` | **待确认**。若选择 CNY 等币种，真实支付开发前先修订统一定价与兑换规则。第一版不做多币种混用 |
| 自助结算路径 | 租号、续费只用积分 | 充值与消费是两类订单；充值成功不等于号码已开通 |
| 过期与赠送 | 积分不过期；第一版不开放充值赠送 | 补偿积分仍单独记来源，不能退成现金 |
| 充值额度 | USD 假设下，单笔 $5–$500、单用户每日成功充值不超过 $500；可自定义金额，精确到美分 | **建议值，待确认**。限制计算需计入尚未终结支付的额度占用，防止并发绕过；其他币种重新确定数值 |
| 未消费积分现金退款 | 用户可申请，管理员受理；仅退原充值剩余实付权益，原路退回 | 不要求用户必须销户；渠道窗口、法定义务和特殊情况见第四节。默认不从应退本金中扣渠道手续费 |
| 消费顺序 | 先用补偿积分，再按到账时间先进先出使用实付积分 | 消费退款退回原批次，不能把补偿积分变成可退现金积分 |
| 充值后继续 | 保存购买草稿，到账后返回确认页，重新核价、核库存，由用户确认购买 | 不承诺保号，不在后台自动购买；按钮文案明确“充值后返回确认” |
| 后台收费与补偿 | 新增收费统一走用户积分消费；后台开通/延期默认仅作为有原因的免费补偿 | 第一版关闭新增“填写线下实收金额直接开通/延期”；历史记录不变。若必须继续线下收费，应在审核时调整范围 |
| 账户关闭或受限 | 不直接删除资金记录；受限账户仍可查账，由管理员处理合法退款申请 | 实付余额不能因封禁或关闭账户而自动清零 |
| 业务日期 | 业务报表与用户日限额统一使用 `Asia/Shanghai`，渠道原始时间和账单区间另行保留 | 建议值；页面标明时区，避免将服务器本地时间隐含当作业务日 |

用户整体审核通过且未对建议值提出修改时，以表内建议作为第一版实施基线，无需逐项再次确认。尚未提供的主体、经营地区和渠道准入信息，在真实渠道接入前补齐；不阻塞已批准币种和比例下的账户及模拟流程开发。模拟配置不能自动成为生产收款配置。

## 三、用户实际使用流程

1. 顶栏和“积分”页显示**可用积分**；存在冻结时，另显示冻结积分及原因。
2. 点击充值，选择档位或输入金额，服务端计算并返回应付金额、币种和到账积分。用户确认后进入支付页。
3. 支付返回后显示“正在确认支付”，轮询自己的充值单；只有服务端确认入账后显示“已到账”。不承诺固定几秒到账，超时应显示查单状态和联系客服入口。
4. 选号或续费确认页显示套餐、积分价、可用余额。余额足够则确认下单；不足则保存草稿，提示充值后返回确认。
5. 返回确认页后，重新检查号码、价格和续费资格。原号不可用时引导重新选号，不重复充值；价格变化时先让用户确认新价格。
6. 消费提交后显示“积分已冻结，正在开通/续费”；成功后变成已完成，失败后解除冻结；结果未知时显示“正在核对”，保留查询入口。
7. 积分明细可查看充值、消费冻结、确认扣款、解冻、消费退款、现金退款和补偿记录；充值记录与消费订单分开。
8. 用户可从原充值单申请退款，看到可申请金额、处理状态和原路退回结果。第一版由管理员审核发起，不要求全自动退款。

## 四、资金、消费和退款规则

### 4.1 账户与积分来源

- 每个用户一个 `PointAccount`，保存 `availablePoints` 与 `frozenPoints`；用户持有积分总额等于二者之和。
- 两个余额均为非负整数。冻结积分不能再次消费、退款或被普通管理员调减。
- 每次发放形成一个来源批次 `PointLot`：`PAID`（真实充值）、`COMPENSATION`（补偿）、`DEMO`（演示）。批次保留原充值、币种和兑换快照。
- 消费冻结时记录从哪些批次扣了多少积分。推荐按“补偿优先，实付批次先进先出”分配；释放和消费退款沿原分配退回。
- 模拟资金仅存在隔离的演示/测试环境；生产接口拒绝 `DEMO` 来源入账。演示记录不参与真实收款、可退款金额和财务报表。
- 关闭充值、修改快捷档位或套餐价格，不影响已有余额、已创建充值单及消费订单的快照。

### 4.2 金额、价格与快照

- 法币金额用最小货币单位整数保存，如 USD 用美分；积分也用整数。禁止使用浮点乘法直接计算到账积分。
- 按本版建议比例，充值 `amountMinor` 美分即到账相同数量的积分；部分退款每核销 1 个该批次积分退 1 美分，不存在四舍五入差额。
- 第一版上线真实实付积分后，后台不得直接修改交易币种和兑换比例。后续如需变更，单独设计新规则及批次兼容方案；本版仍保存快照以便追溯。
- `Plan` 增加 `pointsPrice` 和版本号。确认页使用服务端报价及版本；提交时再次验证，发生变化返回 `PRICE_CHANGED`，用户确认后重试。
- 消费订单在创建并冻结积分时固化套餐、积分价、参考法币价、币种与版本；之后不因套餐改价、下架而改变该订单价格。
- 首页的“约合金额”按已确认的兑换规则展示，不表示可以直接现金购买；历史订单显示自己的快照。

### 4.3 充值现金退款

1. 现金退款必须指向一笔已成功支付的原充值，不能按全账户余额任意指定退款来源。
2. 可退积分来自该充值批次的**可用实付积分**，不含正在冻结、已消费、已退款或已核销部分。补偿、演示积分不退现金。
3. 可退现金同时受“批次可退权益”与“原支付金额减累计已成功退款及在途退款金额”限制；申请和审核时均重新计算。
4. 支持部分退款。用户申请不冻结资产；管理员核准并提交退款时，在一个本地事务里重新校验、冻结对应积分、占用可退金额并创建退款单。若可退金额已低于申请金额，应退回申请让用户重新确认，不能静默缩减退款。
5. 渠道调用在本地事务提交之后执行，使用退款单的固定渠道幂等键。接口返回“受理”不等于退款成功。
6. 确认成功：核销冻结积分，增加原充值累计已退金额，写流水；确认失败：释放冻结及退款额度；结果未知：保持冻结，查单或转人工。
7. 必须原路退款。原支付方式不可退、超出渠道退款窗口等情况转人工处理，并记录证据与处理结果；不自动认定用户失去退款权利。
8. 默认商家承担渠道未退的手续费。强制退款义务、服务违约和争议处理不受“自愿退款仅限未消费积分”这条规则简单排除；由管理员按实际义务处理并记账。

### 4.4 开通失败与消费退款

- 履约前积分是冻结状态。明确失败只需释放冻结，不能再额外发放一次“退款积分”。
- 已确认扣款后因服务异常需要退积分时，创建独立的消费退款/冲正记录，引用原订单及原消费分配，累计不得超过原实际扣款。
- 退回原积分来源：补偿退为补偿，实付退回原充值批次，恢复其未退款的可退权益。不能重复退款或额外增加原充值的现金退款上限。
- 消费退积分不直接调用支付退款接口。用户随后申请现金退款时，再走原充值的退款流程。
- 结果未知不等于失败。供应商超时、工作进程中断、请求响应丢失时，先查单确认，不能既释放积分又让号码最终交付成功。

### 4.5 管理员调整与拒付

- 手动加分默认仅生成不可退现金的补偿积分，需管理员权限、原因、业务凭证/关联单号、限额与审计；不得通过普通调账伪造真实收款。
- 普通减分仅可扣可用补偿积分，不能扣冻结或实付积分。实付差错走关联原业务的受控冲正、退款或争议处理，不提供无依据的“改余额”入口。
- 付款拒付、资金撤回等外部事件单独记录。可冻结争议充值批次剩余权益；已消费而无法追回的部分记录待处理金额，限制新增消费并转人工，不强行写负余额，也不能忽略渠道已扣回的钱。
- 争议撤销、赔付或核销均保留原事件与处理证据，用追加记录修复；不能删除原流水。

### 4.6 金额示例（采用建议的 USD 比例）

用户充值 $10 得到 1000 实付积分，另获 200 补偿积分。购买 300 积分套餐时，冻结 200 补偿积分和 100 实付积分；明确失败则原样释放，成功则扣除这两部分，剩余 900 实付积分。

此时申请退 $5：核准后冻结原充值的 500 实付积分，剩余 400 可用积分；渠道确认退款成功后核销冻结，累计退现金 $5。若退款结果未知，这 500 积分继续冻结。之后该消费获批全额退积分，则退回原来的 100 实付积分和 200 补偿积分；实付批次又有 500 积分可申请退 $5，补偿的 200 积分仍不能退现金。原充值累计现金退款始终不超过 $10。

## 五、数据模型与一致性要求

本节为目标结构，实施时据此细化 Prisma 字段与迁移。采用独立账户表，替代初稿只在 `User` 上增加一个余额字段；不同时维护两个余额来源。

| 实体 | 关键内容与约束 |
|---|---|
| `PointAccount` | 用户唯一；可用、冻结余额；账户状态；流水序号。余额非负；同一用户的资金修改串行执行 |
| `PointLot` | 来源、关联充值/补偿、初始发放、当前可用与冻结、币种/比例快照；实付批次与充值入账唯一关联 |
| `PointLedger` | 账户内连续序号；可用/冻结各自变动与变动后余额；业务类型、业务单、操作者、原因、发生时间；业务唯一键防重 |
| `PointAllocation` | 冻结、消费及退回涉及的批次和积分数；关联消费订单/退款与原分配，支持按原来源退回 |
| `RechargeOrder` | 用户、应付金额、币种、固定到账积分、规则快照、状态、过期时间、累计退款信息、用户幂等键及请求指纹 |
| `PaymentAttempt` | 关联充值单；渠道、商户/账户、渠道支付意图、应付金额、币种、状态、渠道幂等键、查单/重试及认领信息 |
| 实际渠道交易记录 | 关联支付尝试、每笔实际扣款标识、实收金额/币种和资金去向；支持登记额外扣款，不覆盖前一笔成功交易 |
| `PaymentEvent` | 渠道、商户/账户、事件 ID、事件种类、必要原始证据与摘要、验签/处理结果、重试时间、冲突信息；事件身份唯一 |
| `RefundOrder` | 原实际支付交易/充值、退款种类、申请人、受理管理员、金额、积分冻结分配、渠道退款标识、幂等键、状态、失败/未知原因、时间。区分积分兑换退款与未入账额外收款的退款，后者不冻结积分 |
| 消费订单扩展 | `pointsAmount`、结算类型、套餐/报价快照、独立资金状态、供应商请求标识、认领与重试信息；保留已有历史金额字段 |
| 消费退款记录 | 原消费订单、原分配、已退积分、原因、状态、业务幂等键；不与现金退款共用含糊的“退款”流水类型 |
| `PurchaseIntent` | 用户绑定的选号/续费草稿、租期、号码或租约、报价版本、期限及完成状态；不能作为库存预留或已付款证明 |
| 对账/异常记录 | 对账批次、渠道账单项、差异类型、关联业务、金额/币种、处理状态、责任人及证据；支持拒付等金融异常 |
| `Plan` / `AppSetting` | 积分价格、版本；充值开关、固定币种/比例、档位、额度、频率限制。规则变更审计；密钥不放在普通设置中 |

### 5.1 必须实现的约束

- 用户业务幂等键按用户和操作域约束，保存请求指纹；相同键相同请求返回原结果，不同请求返回冲突。优先查已存在的业务结果，再做新单价格/规则校验，避免改价后同一旧请求无法恢复。外部渠道使用独立且稳定的幂等键。
- 同一充值的入账流水业务键唯一；同一消费的确认、解冻、退回及同一退款的核销各有独立唯一业务键。不能只靠渠道流水号唯一防重复加分。
- 渠道交易、事件、退款标识至少按“渠道＋商户/账户＋渠道 ID”唯一；沙箱与生产环境隔离，不能混用事件或密钥。
- 同一资金事务内更新账户、批次、分配、流水和业务状态；金额/积分校验失败则全部回滚。
- 锁顺序统一为目标用户 → 积分账户 → 号码（如有）→ 业务单及批次（稳定顺序）；原后台路径同步调整。先读定位信息，取得锁后重新校验，不持锁调用上游。
- 扣减必须校验可用余额、批次余额和当前业务状态，使用条件更新及数据库非负约束兜底。并发消费、退款、调账不能超扣。
- 所有额度、金额、积分均校验整数、范围与溢出。接口不接受客户端指定到账积分、可信价格或任意用户 ID。
- 用户只可访问自己的账户和单据；管理员写操作有权限、原因、审计与防重。

### 5.2 账本核对与修复

- 账户可用、冻结余额分别等于各批次对应余额之和；流水按序累加，应与账户余额一致。
- 在途冻结分配之和应等于对应业务尚未处理的冻结积分；成功消费、成功退款均可追溯到原发放来源。
- 单笔充值只发放一次；同一原支付的成功及在途现金退款不得超过其实际成功支付金额。
- 流水只追加，不能直接修改、删除。发现差异先限制相关资金写入，保存证据；管理员通过关联原业务的冲正修复，不能直接把余额改成“看起来正确”。

## 六、状态流转

支付状态、积分入账状态、消费履约状态和退款状态分别保存，不用一个“成功/失败”代表所有结果。

### 6.1 充值与支付

| 对象 | 状态 | 规则 |
|---|---|---|
| 充值单 | `PENDING` | 已创建，尚未入账；一次支付尝试失败不必立即判整单失败 |
| 充值单 | `CREDITED` | 已验证收到匹配的付款，积分入账事务已提交；不会因旧失败通知退回待支付 |
| 充值单 | `EXPIRED / CANCELED` | 不再允许开启新的支付；不代表渠道一定没收到钱。已成功的迟到付款仍需核实处理 |
| 支付尝试 | `CREATED / PROCESSING` | 渠道创建或用户付款处理中 |
| 支付尝试 | `SUCCEEDED / FAILED / CANCELED` | 经渠道证据确认的结果；前端返回参数不能确定状态 |
| 支付尝试 | `UNKNOWN` | 请求超时或结果无法确认，继续查单，不能盲目创建第二笔支付 |

充值单的退款汇总状态单独显示“未退／部分已退／全部已退”，异常标记也单独保存；退款不覆盖“曾经成功入账”的事实。状态迁移需按渠道对象版本及事实核验，不能简单按事件到达先后覆盖。

第一版一笔充值单只允许一个有效渠道支付意图，支付页内重试复用该意图。确需替换意图时，先确认旧意图已关闭。任何额外成功扣款都须留存独立交易证据，进入异常处理并原路退款；不能覆盖原流水号或为同一充值再次发积分。对此类“未发积分的额外收款”退款，不从用户已有积分中再扣一次。

### 6.2 现金退款

| 状态 | 积分/资金动作 |
|---|---|
| `REQUESTED` | 用户提出申请，尚未冻结；可取消申请 |
| `REJECTED / CANCELED` | 未提交渠道，记录原因；若已有冻结，须确认尚未发出退款并阻止任务再发送后，一次性解冻与释放额度 |
| `PENDING` | 管理员核准，冻结积分与可退金额，等待调用渠道；重复提交返回原退款单。未入账额外收款退款仅占用原支付可退金额，不冻结积分 |
| `PROCESSING` | 渠道已受理，等待最终结果 |
| `UNKNOWN` | 结果未知；维持冻结和退款额度占用，主动查单或人工核实 |
| `SUCCEEDED` | 一次性核销冻结、记现金退款流水及累计已退金额 |
| `FAILED` | 确认渠道未退款后一次性解冻并释放额度；重试创建有明确关联的新操作 |

退款请求一旦可能已发给渠道，就不能仅凭本地取消将积分解冻；必须先确认渠道未退款。对账发现“本地已失败、渠道实际已成功”时进入资金异常流程，不盲目再次退款。

### 6.3 消费资金与履约

| 履约状态 | 资金状态 | 后续动作 |
|---|---|---|
| 待处理/处理中 | `RESERVED` | 积分已冻结，尚未最终扣款 |
| 开通/续费成功 | `CAPTURED` | 核销冻结并写消费流水；成功租约或续费结果同时落库 |
| 明确失败 | `RELEASED` | 原批次解冻，不创建成功租约或延长到期时间 |
| `UNCERTAIN` | 维持 `RESERVED` | 查供应商结果，不重发可能已成功的购买/续费，不自动退款 |
| 已消费后获批退积分 | `PARTIALLY_REFUNDED / REFUNDED` | 按原消费分配退回，记录独立消费退款 |

演示状态 `DEMO_CONFIRMED` 继续明确标记为演示；真实订单使用真实履约结果，不能去掉文案后直接视为生产开通。

## 七、充值、回调与任务恢复

### 7.1 创建充值

1. 登录校验、账户状态校验；服务端读取启用规则，检查金额、币种、日额度与频率。
2. 使用用户幂等键创建充值单和持久化支付创建记录；固定金额、积分、规则快照与渠道幂等键。确认响应丢失时重试同一请求，不生成第二单。
3. 在数据库事务之外调用渠道创建支付。网络超时记为未知，按原幂等键查询/恢复；不把未知当成创建失败。
4. 保存渠道支付意图后返回支付链接。不得接受客户端任意跳转地址，支付返回路径采用站内允许列表。
5. 建议充值单本地有效期 30 分钟；该期限不代替渠道关闭与实际支付状态。

### 7.2 回调与主动查询统一入账

1. 回调按最终渠道要求验证原始请求签名、商户身份、事件时效；保存必要事件证据及处理状态，避免长时间阻塞回调响应。不存储卡号等非必要支付敏感数据。
2. 验证成功的回调或服务端认证查单都进入同一个领域处理函数，前端“支付成功”只能触发查询。
3. 确认对应原充值、商户/账户、成功交易、金额与币种；不匹配时不加分，记录异常并提醒管理员。
4. 在一个本地事务中锁定账户与单据；验证尚未入账，完成条件状态迁移、发放实付批次、增加可用积分、写唯一入账流水及事件处理结果。
5. 重复事件、不同事件报告同一笔付款、回调与查单并发，均返回已有业务结果，不重复加分。
6. 同一事件 ID 出现不同内容时记录冲突并查证，不能直接覆盖已保存证据。

### 7.3 过期与迟到付款

- 定时检查待支付、未知和本地过期但渠道未确认关闭的记录。到期后先查单，再按渠道能力关闭支付；与渠道成功付款竞争时，仍以查证后的事实处理。
- 迟到但真实成功、金额币种完全匹配的付款，建议仍按原快照入账并标记迟到；不能因本地过期丢弃已收款。
- 因账户限制或无法匹配业务而不宜直接入账的成功收款，进入待处理资金记录，由管理员核实后入账或原路退回，不静默丢弃。
- 不能仅扫描 `PENDING` 后永久放弃过期记录。渠道账单还要检查系统未入账或未识别的成功收款。

### 7.4 持久化任务与恢复

- 支付创建、事件处理、查单、退款提交、退款查询和履约核对应由数据库状态与重试记录驱动；进程重启后可恢复，不只依赖内存计时器。
- 可复用现有认领令牌、`claimUntil`、重试次数等模式；多实例不能重复执行资金动作。外部调用结果不明时，先查单再决定是否重试。
- 重试设置退避及频率上限，超过自动处理范围转人工并告警；不能因达到重试次数就判定支付/退款/开通失败。
- 原有任务恢复逻辑需接入新资金状态，尤其是过期认领恢复为 `UNCERTAIN` 时保持对应冻结。

## 八、租号与续费

1. 用户提交号码/租约、套餐和报价版本，并携带独立消费幂等键；后端重新核对价格、可售库存、归属、账户状态及续费资格。
2. 本地事务中冻结足额积分、登记批次分配、创建消费订单，按现有独占规则占用号码。余额或库存不足时整笔回滚，不生成半成品扣款。
3. 提交后调用供应商；供应商调用使用订单唯一请求标识，不能因前端重试再次购买。
4. 成功结果在本地事务中确认扣款及租约/续费结果。新租约服务起点依据真实供应商的服务确认规则，不以充值时间或等待中的订单时间起算；续费按实际确认的服务截止时间更新。
5. 明确失败释放冻结和可释放库存；结果未知保留资金及号码占用，查单后收敛。对长期未知订单给出管理员处理入口和证据，不承诺固定时间自动退款。
6. 续费提交和供应商执行前复核号码仍归用户、资源可续及当前期限；等待充值期间已过期的租约不能直接沿用原确认页成功续费。
7. 并发续费须串行或明确拒绝第二笔在途续费，不能重复延长或重复扣分。
8. 模拟渠道遵循同一领域状态和账本规则；真实供应商适配未验收时，仅能演示，不开放真实付费消费。

## 九、充值后返回确认页

- 保存服务端 `PurchaseIntent`，绑定用户，默认 24 小时有效；可用站内草稿 ID 恢复。前端本地缓存仅用于体验，不作为扣款依据。
- 草稿包含业务种类、选中号码/租约、租期、报价版本和返回位置；切换账号不能访问他人的草稿。
- 充值单可关联草稿，便于支付返回后定位；充值成功与草稿过期、库存失效分别处理，不因买不到原号而撤销已正确到账的充值。
- 第一版不在充值期间预留号码。提示“充值后会重新检查号码是否可用”；原号失效引导重新选择，余额保留可用，用户也可按规则申请退款。
- 返回页面重新获取报价，展示本次实际所需积分和余额，让用户再次确认。刷新、返回、多标签页和重复确认通过同一业务幂等机制处理。
- 草稿确认形成订单后记录消费订单 ID。即使订单仍在开通中，重复提交同一草稿也只能返回该订单，不能创建第二笔消费。

## 十、页面、接口与管理操作

### 10.1 用户端

- 顶栏、工作台：可用积分；有冻结时可查看对应订单。
- “积分”页：可用/冻结余额、明细、充值记录、退款记录及申请入口。
- 充值弹窗：金额、币种、到账积分、支付方式、额度提示；以服务端计算结果为准。
- 支付结果页：待支付、确认中、已到账、过期/关闭、待人工核实；未知状态优先提供查询，不能诱导重复付款。
- 选号、续费：积分价格、余额、报价变化、冻结与履约进度；不足时保存草稿并跳充值。
- 历史账单按结算类型显示现金/积分/补偿/演示，不把旧记录强行改成积分订单。

### 10.2 管理后台

- 充值规则：开关、档位、额度及频率；币种和比例上线后锁定。规则变更记审计。
- 充值、支付、退款详情：展示各自状态、渠道标识、证据、查单结果与关联资金流水；按用户、时间、状态筛选。
- 退款管理：用户申请、审核、部分退款、进度核对、失败原因；提交前显示实际将退金额与将冻结积分，并二次确认。
- 用户详情：余额及冻结来源、来源批次、流水、受控补偿加减分；不能直接编辑余额。
- 异常处理：迟到付款、已付未入账、回调冲突、未知退款、拒付、长期未知履约；每项指定处理状态和审计记录。
- 对账与概览：按实际交易币种区分充值收款、现金退款、净收款、积分消费、补偿发放及历史线下收款；渠道手续费、结算差异单独展示。

### 10.3 最小接口范围

接口名称可在实施时遵循现有项目风格调整，但下列行为与权限不能省略。

| 操作 | 权限与要求 |
|---|---|
| 查询积分账户、流水、充值/退款记录 | 登录用户本人；历史分页，不能用前端过滤代替鉴权 |
| 创建充值、查询支付状态 | 本人；创建幂等，查询限流；金额和到账积分由后端决定 |
| 接收支付/退款回调 | 渠道验签身份；不依赖用户登录；必须有事件防重和重试记录 |
| 保存/恢复/提交购买草稿 | 本人；校验有效期、报价与库存；同草稿只能形成一笔消费 |
| 申请现金退款、查询申请 | 本人；申请不代表退款已受理或成功 |
| 管理员审核退款、查单、补偿、处理异常 | 管理员权限、原因、审计、幂等；资金动作重新校验当前状态 |
| 模拟付款、模拟退款、模拟供应商结果 | 仅隔离的非生产演示环境；服务端禁止在生产注册或执行 |

## 十一、与现有数据和功能的衔接

### 11.1 套餐、旧账户与历史订单

- 按已批准比例初始化 `Plan.pointsPrice`。在 USD、1 美分对应 1 积分的假设下，可由现有 `priceMinor` 初始化；执行前展示价格映射，由管理员核对，不擅自改变套餐实际价格。
- 已有用户初始可用/冻结积分均为 0；历史订单、模拟付款、号码资产不自动换成积分。
- 旧租约到期时间、归属和原价快照保留；只有新提交的积分消费进入新账本。
- 新消费增加结算类型与 `pointsAmount`。旧 `amountMinor / priceMinor` 保留原历史/参考价格含义；积分订单中的参考法币价不等于该订单收到现金。页面和报表必须按结算类型解释，不能继续直接合计成收款。
- 演示历史保持演示标签，后台报表默认排除演示数据；不通过批量更新状态制造真实成功记录。
- 保持已有订单幂等键和请求指纹的兼容语义；字段、算法或操作域调整不能导致历史请求被误判成新单或无法查询原结果。

### 11.2 现有 `Payment` 与充值支付

- 第一版新增专属于充值的 `PaymentAttempt`，与 `RechargeOrder` 关联；不把充值伪装成租号 `Order` 来满足现有 `Payment.orderId`。
- 现有 `Payment` 保留历史查询，不与积分账本共享“成功即消费成功”的含义。若以后统一支付模型，另做兼容迁移，不作为本版上线前置重构。

### 11.3 后台开通、延期与线下实收

- **建议调整**：停止新增“填写线下实收金额直接开通/延期”；接口不能只隐藏输入框，必须阻止这条新增收费路径。
- 管理员免费补偿开通/延期仍保留，要求原因与审计，标记 `ADMIN_COMPENSATION`，不制造现金收入，也不重复赠送积分。
- 用户付费统一通过其账户充值和自助积分订单；管理员不得未经明确授权替用户扣积分购买。
- 现有线下实收历史继续可查、单独统计。以后需要继续收线下款时，单独补充收款凭证、审核、入账幂等和退款责任，不能用普通补偿加分代替。

### 11.4 概览与财务口径

- 停止用“成功消费订单金额之和”代表充值收款；也不将充值与积分消费重复相加。
- 业务报表至少分列：真实充值收款、现金退款、净收款、积分消费量、未消费实付积分权益、冻结积分、补偿积分、历史线下收款、渠道手续费。
- 充值收款不直接等同会计收入确认，相关财税和凭证口径在真实上线前确认；本系统先提供可核对原始事实。
- 交易币种、渠道结算币种不同的账单分别记录，不直接相加；第一版选择渠道时确认是否需要额外支持换汇结算差异。
- 按已批准业务时区定义“今日”；本版建议 `Asia/Shanghai`。支付成功按渠道确认的付款时间归属业务日，保存 UTC 原始时间；渠道账单按其原始区间另行核对，页面明确展示口径。

## 十二、对账、限额与上线运行

### 12.1 对账与异常闭环

- 日内主动查单解决未到账、未知支付和未知退款；每日拉取渠道可用账单，双向核对本地与渠道记录。
- 差异至少覆盖：渠道成功但本地未入账、本地已入账但渠道不匹配、金额/币种不符、重复扣款、退款状态或金额不一致、拒付、手续费与结算差异。
- 对账差异落数据库，记录处理人、依据、结果及关联冲正/退款；“已处理”必须有实际动作或明确核实结论，不能只改列表状态。
- 查不到正式账单的渠道，也须提供受控导入官方账单并复核的操作方法；真实上线前完成一次有收款和退款的完整对账。

### 12.2 基础限额与保护

- 单笔、单用户每日额度按第二节审核值执行。新建支付时，在用户锁内校验“该业务日成功付款金额＋该用户所有未终结支付占额＋本次金额”不超过上限；同一支付不能重复计入成功与在途。
- 创建支付占用额度，成功转为按付款时间归属的已用额度；未知不释放，确认关闭/失败才释放。跨日未终结支付也继续占用当前可用额度，避免日切绕过限制；处理确认结果后再重新计算。
- 迟到成功付款必须记账或退回；即使造成当日超额，也不能以限额为由丢弃收款。记录异常并限制后续新增交易。
- 建议初始限制：单用户每分钟最多创建 5 笔充值单，同时最多 3 笔尚未确认终结的支付；叠加必要的 IP 频率限制，数值可审计调整。
- 退款不自动恢复当天充值额度，防止充退循环；低于渠道最低退款金额等情况需明确展示并转人工，不能吞掉差额。
- 系统可分别关闭新增充值、新增消费；已收到的回调、查单、退款、解冻与核对任务仍须运行。

### 12.3 恢复、告警与运维

- 使用 HTTPS；密钥保存在环境密钥配置中，限制权限和日志输出；回调地址、签名密钥及商户账户先在沙箱验证，再切生产。
- 对到账积压、未知退款、账本差异、对账差异、长期冻结和回调验签异常设置通知与人工处理入口；不能只写服务器日志。
- 数据库备份覆盖资金记录，演练恢复后任务和幂等继续有效；保存渠道证据便于恢复后重新对账，不能重复入账或退款。
- 明确退款受理与异常值守负责人、处理入口及对外联系方法；对用户展示可追踪单号，不展示内部密钥或供应商调试信息。

## 十三、分阶段实施与交付

工期在用户批准业务规则、确定渠道及拆分任务后估算。本稿不把渠道审核或生产联调写成固定 1–2 周。

| 阶段 | 工作与交付 | 依赖 | 达成后的使用边界 |
|---|---|---|---|
| 1. 积分账户与消费基础 | 数据迁移、余额/冻结/来源批次/流水、积分价格、购买与续费的资金状态、受控补偿、用户积分页、旧数据和后台入口适配 | 批准首版币种、比例、消费顺序和后台调整 | 仅开发/演示验证；没有真实充值和付费交付能力 |
| 2. 完整模拟闭环 | 模拟充值、支付未知/迟到/重复事件、原路退款模拟、消费失败/未知、草稿恢复、对账差异与限额、异常处理后台 | 阶段 1；使用隔离模拟资金 | 可做端到端演示和自动化验收，仍不能对真实用户收款 |
| 3. 真实渠道沙箱与真实供应商联调 | 同事实现渠道支付、验签、查单、关单、退款、账单及争议事件适配；我方连接统一业务接口，验证积分入账/退回及真实租号/续费的交付与失败补偿 | 同事提供可用渠道接口及可信事件约定；具备供应商联调权限 | 仅联调；真实收款上线仍受下一阶段条件约束 |
| 4. 上线验收与小范围运行 | 生产配置核验、小额真实收款/退款/对账、限额和告警、恢复演练、协议与客服准备、受控范围验证 | 前三阶段及第十四节全部必要条件 | 验收通过后才逐步开放 C 端充值；初期小额度、可关新增业务 |

具体渠道的商户配置、API/SDK、回调验签、支付与退款查单、账单和争议通知适配由同事实现；我方保留统一业务接口、模拟适配和账本处理。接口至少能创建支付、查询支付、发起退款、查询退款，并提供已验证的交易/事件标识、商户身份、金额、币种及状态；事件通过受信任的服务端入口交接，不能由前端自报“已验签”来入账。双方开发前对齐这份小接口约定，无需让用户逐项审核技术字段。

同事的渠道接入可与阶段 1、2 并行；接口就绪后双方验证完整真实流程，再按第四阶段开放真实支付。模拟渠道复用领域规则，真实接入仍需完成支付与资金业务的共同验收。

实施时先形成字段/接口与迁移清单，按阶段验证；每阶段报告实际可用入口、测试结果及仍依赖的外部能力，不用 Mock 的成功代替真实交付。

## 十四、验收标准与正式上线条件

### 14.1 必须覆盖的验收场景

以下是预期结果，不代表当前已经通过。

| 场景 | 通过标准 |
|---|---|
| 创建充值/消费响应丢失后重试 | 同一幂等请求返回原单；不同请求复用同一键被拒绝；不重复调用或扣款 |
| 重复回调、多事件指向同付款 | 只发放一个积分批次、一次入账流水 |
| 回调与查单同时确认成功 | 仅一次入账，其余返回已处理结果 |
| 伪造、验签失败、金额/币种/商户不匹配 | 不入账；异常可追踪，不信任前端成功参数 |
| 乱序事件或同事件 ID 内容冲突 | 成功事实不会被旧失败覆盖；冲突保留证据并核实 |
| 本地到期/取消后渠道实际付款成功 | 能查到、核实并入账或原路退回，不丢款、不重复加分 |
| 支付创建超时、进程崩溃 | 按原意图/幂等键恢复，不盲目生成第二个支付 |
| 额外成功扣款 | 独立登记并处理原路退款；不二次发积分、不额外扣用户已有积分 |
| 并发消费、退款、管理员调整 | 账户及批次不出现负数，冻结不被挪用，不超额现金退款 |
| 积分不足、号码抢占失败 | 订单、冻结、库存变更整体回滚，不产生实际扣款 |
| 供应商成功但响应丢失 | 保持未知并查证，只完成一次交付与扣款 |
| 供应商明确失败 | 一次性释放原冻结，不重复补发积分或创建成功租约 |
| 同租约并发续费、等待期间过期 | 按明确规则阻止重复在途续费；过期/不可续时不扣分并返回原因 |
| 部分现金退款、重复退款申请 | 只冻结本批次可退权益；累计在途和成功退款不超过原支付 |
| 退款受理后超时、重启、重复成功事件 | 未知时保持冻结；查证后仅核销一次；确认失败才解冻 |
| 消费退积分后再申请现金退款 | 按原来源恢复权益，补偿不变现金；不突破原支付剩余退款上限 |
| 拒付时积分已消费 | 记录资金损失/待处理金额与账户限制，不靠负余额或删账掩盖 |
| 跳转支付、整页刷新、多标签页、切换账号 | 可恢复本人的有效草稿，不能越权；同草稿不生成第二笔消费 |
| 充值后号码被占用、套餐改价 | 引导重选或重新确认；不自动扣价差、不强买、不要求重复充值 |
| 余额、批次、流水及对账核对 | 账户、冻结分配、流水可相互验证；差异可定位、审计修复 |
| 日额度并发、跨日、迟到成功 | 在途占额防绕过；迟到收款正确处理并限制新增交易 |
| 关闭充值或消费开关 | 拒绝新增业务；已付款入账、查单、退款与核对照常运行 |
| 后台旧收费入口、历史展示 | 服务端阻止旧路径新增收费；历史线下/积分/补偿/演示分类正确 |
| 生产演示隔离、权限与恢复 | 生产模拟接口不可用；用户无法越权；备份恢复后不重复执行资金动作 |

### 14.2 正式向 C 端开放真实充值前

- [ ] 用户已确认第二节各项业务取舍，价格、限额、退款文案与页面一致。
- [ ] 收款主体、服务地区、支付渠道业务准入与允许的支付方式已核验；不存在把渠道申请视为已获批准的情况。
- [ ] 真实租号、续费、可用资源、服务有效期与实际供应商规则已验证，用户付费后有可交付的服务。
- [ ] 充值入账、原路部分退款、拒付/争议处理、查单、对账与资金异常均有可执行流程。
- [ ] 关键并发、异常、权限与恢复场景验收通过，生产模拟入口确实禁用。
- [ ] 完成小额真实支付、到账、消费、退款及渠道对账；沙箱结果和真实结果分别记录。
- [ ] 用户协议、积分性质、退款/服务异常规则、个人信息与必要财税义务已结合实际地区确认；客服和处理负责人就位。
- [ ] 有已演练的数据备份、异常告警、每日核对和关闭新增业务的方法；迁移有预演及恢复依据。

上线前关闭项是业务开关，不以回滚或删除资金记录代替止损。首次出现真实资金后，故障处理优先暂停新增业务、保留回调与查询、修复并核对；涉及资金记录的数据库迁移不得直接回退删表。确认没有真实资金的演示数据才可按隔离环境规则重置。

本版审核通过代表可以按批准范围进入开发；各阶段完成与正式可用分别以实际验收证据判定。
