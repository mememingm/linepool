# WP2-c：余额转账与暂停代理验证说明

## 本包范围

本包覆盖 F5/Q1：直属下级余额转账、下级详情余额展示、余额不足提示、号码转交后的回弹与报价刷新，以及暂停代理不能继续结算。

已保留的既有行为：

- `HoldingDistributionForm` 继续使用时长、金额/结算报价、中文“关闭/转交”文案。
- 财务页的转账入口只在存在 ACTIVE 直属下级时显示；接收方列表来自直属下级，不包含客户。
- 后端继续拒绝客户作为美元余额接收方（`TRANSFER_SCOPE_INVALID`）。
- 转账继续使用余额账户行锁、双方账本记录和幂等键语义。

  - 一级代理目标必须是自己的直属下级且状态为 `ACTIVE`；暂停/终止目标返回 `409 AGENT_NOT_ACTIVE`。

## WP3 合并后验收清单（唯一写操作测试人执行）

> 本 worktree 只做静态检查，不能把主服务或旧构建产物的结果当作本包运行验收。WP3 测试人应在合并全部工作包后使用受控测试账号和备份库执行以下用例，并保存请求/响应及数据库快照证据。

### 1. 暂停目标拒绝且无副作用

1. 记录一级代理余额、暂停目标下级余额，以及双方 `balance_ledger`、`tx_orders` 最近记录。
2. 将直属下级状态改为 `SUSPENDED`，不重启服务。
3. 用一级代理调用 `POST /api/agent-inventory/transfers`，目标为该下级，金额例如 `5.00 USD`，带全新的幂等键。
4. 预期：HTTP `409`，错误码 `AGENT_NOT_ACTIVE`。
5. 再次查询余额、订单、双方账本：余额和账本余额不变，不新增 COMPLETED 转账订单，不新增 TRANSFER_IN/TRANSFER_OUT 流水。
6. 并发窗口应覆盖“暂停请求与转账请求同时到达”的情形；目标代理行锁保证转账不会绕过暂停状态。

### 2. 恢复后重新登录并成功转账

1. 将目标代理恢复为 `ACTIVE`；暂停会撤销其旧 session，因此目标代理必须重新登录，不复用旧 cookie。
2. 重新登录后确认下级工作台可访问。
3. 一级代理转账 `5.00 USD`，使用新幂等键。
4. 预期：HTTP `201`/成功响应；一级余额减少 `5.00`，下级余额增加 `5.00`。
5. 双方各新增一条对应账本记录，转账订单状态为 `COMPLETED`。
6. 在下级详情页确认余额立即刷新；号码转交弹窗内执行“给 TA 转余额”后，返回原弹窗时原号码、使用时长、金额和接收方仍保留，报价按新余额刷新。

### 3. 同幂等键重试只结算一次

1. 对 ACTIVE 目标提交一次成功转账，保存请求体和幂等键。
2. 使用完全相同请求体和幂等键重试一次或多次。
3. 预期：返回同一转账订单结果，不新增订单；双方余额各只变化一次；双方账本各只新增一条该订单对应流水。
4. 使用同一幂等键但修改金额或接收方，预期返回 `409 IDEMPOTENCY_CONFLICT`，不产生余额或账本变化。

### 4. 客户目标拒绝

1. 以代理身份直接调用余额转账接口，将 `toOwner` 设置为 `CUSTOMER`。
2. 预期：请求被拒绝，错误码 `TRANSFER_SCOPE_INVALID`；不新增订单、不改变任何余额、不写入转账流水。
3. 财务页接收方下拉不得出现客户；没有 ACTIVE 直属下级的代理不显示“转余额给下级”入口。

## 静态验证边界

- 允许：`npm run typecheck`、`npm run api:typecheck`、构建和源代码检查。
- 禁止：测试套件、`npm test`、迁移、SQL 写入、重启共享服务、真实上游或支付调用。
- WP2-c 执行人不在旧主服务上宣称新代码已实测；实际运行结果由 WP3 合并后唯一测试人记录。
