# PC → LinePool API 对接清单

> 版本：2026-11-02 · 发给 PC 负责人确认
>
> PC = PingCode 上游；LP = LinePool。本清单按批量供号方案编写（资源占用边界须 PC 确认），覆盖 LP 本地销售与分配、接收短信、库存与短信对账，以及号码续费和用量查询；不接用户支付。
>
> 本文区分「LP 当前已实现」与「建议契约 / 待 PC 确认」。PC 查询接口的路径、字段示例均为建议，接受已有接口提供等价能力；不能据此认为上游已经实现。短信 Webhook 部分按 LP 当前源码核对，尚未完成真实联调。

## 2. 先确认业务和标识规则

这些规则决定号码是否能销售，以及短信能否送给正确客户。

- [ ] **供货模式**：按批量供号对接；PC 说明交付给 LP 的资源范围，是否还会向其他渠道分配同一号码、同一项目的服务。
- [ ] **占用边界**：明确独占的是整张卡、手机号，还是「项目 + 号码」；跨平台能否同时用、同平台能否多人同时用。若资源并非专供 LP，须有上游原子占用/锁定机制，不能仅靠库存查询避免重复销售。
- [ ] **资源标识**：`projectId` 稳定；`numberId` 指向稳定资源，不把同一 ID 改指另一个号码。手机号回收、更换或资源重新交付时，说明 ID 与可用时段如何变化。
- [ ] **短信和事件唯一性**：`messageId`、`eventId` 在接入 LP 的所有项目/账号范围内唯一。LP 当前按 provider 级别去重；如果 PC 只能保证项目内或账号内唯一，需提供命名空间，由双方调整映射后接入。
- [ ] **跨项目短信**：若一条物理短信关联多个项目，说明归属依据和消息 ID 分配规则。当前 LP 不接受同一 `messageId` 指向不同项目，不能靠修改 ID 把归属不明的短信广播给多个客户。
- [ ] **租期**：明确资源何时开始可用、何时失效，以及以哪个时钟为准；LP 售出的服务结束时间不能超过 PC 资源有效期。到期不自动续费。
- [ ] **释放含义**：区分 LP 客户租期结束、LP 本地重新分配、PC 回收底层资源；明确哪些动作需要通知 PC，及重新出售是否需要等待期。
- [ ] **成本**：说明按号码、项目、时长还是短信计费；提供币种、金额单位、精度、价格生效时间和失败是否收费。没有确认的成本应标为未知，不按 0 成本计算真实利润。用户支付不在本次对接范围内。

## 3. PC 接口的数据要求

### 3.1 通用要求

- HTTPS + UTF-8 JSON；PC 提供正式鉴权说明、凭据配置方法及测试/生产环境区分。凭据通过约定的安全渠道交付，不填进本文。
- ID 建议统一返回字符串，避免长整数丢失精度；缺失值与空值含义需明确。
- 手机号使用 E.164，如 `+12025550100`；时间使用带时区的 ISO 8601，建议 UTC，例如 `2026-11-02T06:00:00Z`。
- 明确 HTTP 状态码、业务错误码、请求追踪 ID；限流应提供可识别的重试时间，如 `Retry-After`。说明请求超时、并发限制和推荐调用频率。
- 列表接口需说明分页上限、稳定排序、游标有效期及完整扫描方式；数据在分页期间变化时，也应有不漏数据的办法。
- 增量同步需覆盖状态变化和撤回；查询失败、分页未完成、过滤结果为空均不能直接解释为“所有库存已删除”。只有完成且范围明确的权威快照才能据此对账。

### 3.2 项目清单（建议响应）

```json
{
  "items": [
    {
      "projectId": "project_telegram_001",
      "name": "Telegram",
      "platform": "telegram",
      "status": "active"
    }
  ],
  "nextCursor": null
}
```

必需信息：项目稳定 ID、名称/平台映射、启停状态。PC 给出完整枚举和大小写；`telegram` 是建议映射值，不要求 PC 修改内部名称。若一个项目支持多个平台，需要明确关系，不能让 LP 猜测。

### 3.3 项目号码清单（建议响应）

```json
{
  "projectId": "project_telegram_001",
  "items": [
    {
      "numberId": "number_10001",
      "phoneNumber": "+12025550100",
      "status": "available",
      "availableFrom": "2026-11-02T00:00:00Z",
      "availableUntil": "2026-12-02T00:00:00Z",
      "updatedAt": "2026-11-02T05:00:00Z"
    }
  ],
  "nextCursor": null
}
```

必须能取得：项目关系、号码 ID、手机号、可用状态和资源有效时段。没有可靠的截止时间时，LP 不应默认可以无限期销售。

建议状态为 `available`、`assigned`、`expired`、`released`、`disabled`，最终以 PC 完整枚举和双方映射为准。尤其要说明：

- `assigned` 是分配给 LP，还是已经被终端用户占用；两者不能混用。
- `released` 是可以重新出售，还是已从 LP 资源池撤回。
- 号码从列表消失意味着什么；是否能查询所有状态或拿到删除/撤回标记。

同一号码支持多个项目时，应返回明确的项目关系。资源从 PC 分配给 LP，不等于 LP 已经分配给某个客户。

### 3.4 漏短信补偿（建议响应）

```json
{
  "items": [
    {
      "messageId": "msg_000001",
      "projectId": "project_telegram_001",
      "numberId": "number_10001",
      "phoneNumber": "+12025550100",
      "from": "Telegram",
      "content": "Your code is 123456",
      "occurredAt": "2026-11-02T06:00:00Z",
      "createdAt": "2026-11-02T06:00:01Z"
    }
  ],
  "nextCursor": null
}
```

- 必须能在**不知道 messageId** 时发现漏掉的短信，例如按项目/号码和时间分页查询，或按事件游标重放。
- 若沿用旧 `/sms` 查询，需补齐项目归属或提供可证明唯一的映射；不能仅按手机号匹配客户。
- `occurredAt` 是 PC 实际收到短信的时间，决定归属；`createdAt` 是记录进入查询系统的时间。迟到入库的短信也要能被增量扫描发现，PC 需明确 `after` 的时间基准和边界是否包含。
- 查询与推送必须使用相同的消息 ID、归属、正文和原始接收时间，避免补偿时被当成另一条消息或引发内容冲突。
- 明确历史保留时长、最大可查询区间、游标失效后的恢复方式，以及终止 Webhook 重试后如何重放。保留时长应覆盖双方约定的最长恢复窗口。

### 3.5 号码续费（建议契约）

LP 网站已有续费页面：客户选择续费时长，LP 扣除本地积分后向 PC 提交续费。卡由 SimFlow 开通、PC 托管，如果续费需要 PC 转给 SimFlow 延长底层资源，请 PC 说明这条链路，LP 只对接 PC。

**查询可续选项**

```http
GET /api/numbers/{numberId}/renewal-options
```

```json
{
  "numberId": "number_10001",
  "currentExpiresAt": "2026-12-02T00:00:00Z",
  "options": [
    { "durationDays": 7, "cost": { "amountMinor": 300, "currency": "USD" }, "estimatedExpiresAt": "2026-12-09T00:00:00Z" },
    { "durationDays": 30, "cost": { "amountMinor": 1000, "currency": "USD" }, "estimatedExpiresAt": "2027-01-01T00:00:00Z" }
  ]
}
```

**提交续费**

```http
POST /api/numbers/{numberId}/renewals
Idempotency-Key: <LP 生成的 UUID>
```

```json
{ "durationDays": 30, "expectedExpiresAt": "2026-12-02T00:00:00Z" }
```

```json
{ "renewalId": "renewal_000001", "status": "pending" }
```

**查询续费结果**

```http
GET /api/renewals/{renewalId}
```

```json
{
  "renewalId": "renewal_000001",
  "numberId": "number_10001",
  "durationDays": 30,
  "status": "succeeded",
  "confirmedExpiresAt": "2027-01-01T00:00:00Z",
  "failureReason": null
}
```

- 可续时长由 PC 返回，LP 不写死 7 天和 30 天；LP 支持 1～365 天的整数天数。
- `expectedExpiresAt` 是 LP 提交时看到的当前到期时间。号码已被续过或已过期时，PC 应拒绝并返回明确错误码，避免重复延长。
- 同一个 `Idempotency-Key` 重复提交只执行一次，并返回同一个 `renewalId`。提交超时后，LP 会用相同的键重试或按 `renewalId` 查询，不会再提交一笔新续费。
- 提交成功只表示已受理。LP 只有拿到 `succeeded` 和 `confirmedExpiresAt` 后，才更新客户号码的到期时间；`failed` 时退回客户积分。PC 说明从受理到出结果通常要多久，以及是否另外推送 `renewal.completed` 事件（当前 LP 入口不接受此事件，启用前需开发）。
- 说明状态的完整枚举、失败原因、成本是否在失败时退回，以及资源已到期多久后不能再续。

### 3.6 号码用量（建议契约）

LP 网站已有用量页面，向客户展示每个号码的短信、语音、流量用量。

```http
GET /api/numbers/{numberId}/usage
```

```json
{
  "numberId": "number_10001",
  "updatedAt": "2026-11-02T06:00:00Z",
  "sms":   { "kind": "metered", "unit": "message", "total": 100,  "used": 36,  "remaining": 64 },
  "voice": { "kind": "metered", "unit": "minute",  "total": 60,   "used": 12,  "remaining": 48 },
  "data":  { "kind": "unlimited", "unit": "MB", "used": 2048 }
}
```

- 每一项的 `kind` 只取 `metered`（有总量）、`unlimited`（不限量）、`no_package`（这个号码没有该项套餐）、`unsupported`（PC 无法提供该项数据）之一。`metered` 时 `remaining` 必须等于 `total - used`（不小于 0）。
- 明确每项的单位（条、分钟、MB 或其他），以及流量是否区分上下行、是否按 1024 换算。
- `updatedAt` 是数据实际统计的时间。PC 说明数据从哪里来（是否由 SimFlow 提供）、多久更新一次、推荐的查询频率和限流。
- 查询失败时返回错误码，不能返回全 0，否则客户会误以为用量已清零。

## 4. LP 短信 Webhook：当前已实现的契约

生产域名、连通性和共享密钥在联调时交付。以下路径已经存在；当前只处理 `sms.received`。

```http
POST /api/webhooks/pingcode
Content-Type: application/json
X-PingCode-Timestamp: <本次发送时的 Unix 秒，10 位整数>
X-PingCode-Event-Id: evt_000001
X-PingCode-Signature: sha256=<64 位十六进制摘要>
```

```json
{
  "eventId": "evt_000001",
  "event": "sms.received",
  "occurredAt": "2026-11-02T06:00:00Z",
  "data": {
    "projectId": "project_telegram_001",
    "numberId": "number_10001",
    "phoneNumber": "+12025550100",
    "messageId": "msg_000001",
    "from": "Telegram",
    "content": "Your code is 123456"
  }
}
```

以上均为示例数据。真实联调使用实际接收时间，不能直接用示例时间验证客户归属。

| 字段 | 当前要求 / 业务含义 |
|---|---|
| `eventId` | 非空字符串，最多 200；重试不变，且必须与请求头相同 |
| `event` | 固定为 `sms.received` |
| `occurredAt` | 带时区的 ISO 8601；原始短信接收时间，重试不更新；不能晚于 LP 当前时间 300 秒以上 |
| `data.projectId`、`data.numberId` | 建议非空字符串，最多 200；当前也兼容正安全整数并转为字符串 |
| `data.phoneNumber` | 带 `+` 的国际号码，后接 7～15 位数字，首位不为 0 |
| `data.messageId` | 非空字符串，最多 200；与补偿查询保持一致 |
| `data.from` | 必填字符串，最多 500；可为号码、短码或品牌名称，不要求 E.164 |
| `data.content` | 必填字符串，最多 16000；正文原样传递，整体请求体仍受下述字节上限约束 |

当前 HTTP JSON 请求体上限为 **16 KiB（16384 字节）**，包括字段名和编码后的正文；中文 UTF-8 可能占多个字节。超限返回 `413`，不能直接截断短信。若 PC 实际消息可能超限，需在联调前协商调整 LP 限制或另定正文获取方案。

### 4.1 签名算法

```text
signedBytes = UTF8(timestamp + ".") || rawRequestBodyBytes
signature   = "sha256=" + HEX(HMAC_SHA256(sharedSecret, signedBytes))
```

- `timestamp` 是本次 HTTP 投递的 Unix 秒，LP 接受前后 300 秒；双方服务器需要校时。
- 使用**实际发送的原始 UTF-8 请求体字节**计算签名；签名后不能重新格式化或重新序列化正文。
- 共享密钥以相同字符串字节使用，双方明确编码和换钥方式；除非另有约定，不进行额外 Base64 解码。
- 不压缩请求体，不发送 gzip/br；当前入口只支持无 `Content-Encoding` 或 `identity`。
- 重试使用新的请求头时间戳并重新签名，保持事件 ID、消息 ID、原始 `occurredAt` 和业务内容不变。
- 连接检查可发送签名正文中的 `test: true`，并保留 `eventId`、`event: "sms.received"`、`occurredAt` 及匹配的事件请求头；这只验证验签和连通性，不入库，不能代替真实短信验收。

### 4.2 响应及 PC 重试规则

成功或一致的重复消息：

```http
200 OK
```

```json
{"received": true}
```

错误体采用 `{"error":{"code":"...","message":"..."}}`；校验错误可能附带 `details`。

| 响应 | 含义 | PC 处理 |
|---|---|---|
| `200` + `received: true` | 已接收；可能已展示，也可能仍待归属匹配 | 停止自动投递重试；不代表客户已经读到短信 |
| `400` | 字段/事件类型错误、事件头与正文不一致、接收时间非法 | 保留失败记录，修复后重放；不原样无限重试 |
| `401` | 签名无效或请求头时间戳过期 | 检查密钥、原始字节、时钟；过期请求应重新签名后投递 |
| `409` | 事件 ID 被用于其他消息，或消息 ID 对应内容/项目变更 | 按数据冲突处理；**不是普通重复事件** |
| `413` / `415` | 请求过大，或格式/压缩不受支持 | 修复双方约定后重放 |
| `429` | 请求被限流 | 按 `Retry-After`（如有）或双方约定退避后重试 |
| `5xx`、连接失败、响应超时 | 暂时不可用，或投递结果不确定 | 使用原事件/消息 ID 重试，刷新签名时间戳 |

PC 确认投递超时、指数退避策略、最大次数/期限、失败保留期限和人工重放方式；这些参数目前尚未共同约定。`503 WEBHOOK_NOT_CONFIGURED` 需 LP 配好密钥后恢复投递。

**未知归属不是 404。** 当前 LP 会保存已验签短信，归属不能唯一确定时不向客户展示；正常保存和处理完成后仍返回 `200`。LP 负责修复映射并重试本地归属。若保存后续处理发生故障，可能返回 `5xx`，PC 用原 ID 重试即可。

### 4.3 短信归属约束

LP 按 `projectId + numberId + phoneNumber + occurredAt` 对照历史分配区间，不能用“当前持有人”接收所有迟到消息。号码分给新客户后，之前收到的短信不能展示给新客户；无法确定唯一归属时保留待处理。

原始短信时间必须可靠。若 PC 无法提供这一时间，需另定可识别资源批次/分配期的契约后再开放复用，不能拿重试时间代替。

## 5. 号码状态同步

首发至少有一种能对账的权威来源：可分页查询全部相关状态，或可重复获取完整且有明确范围的快照。仅查询 `available` 不足以判断号码消失原因。

双方确认同步频率、最大可接受延迟、乱序处理及撤回规则。LP 在已知过期或不可用时停止新分配；客户租期和 PC 资源有效期分别记录。

`number.status_changed` 可降低延迟，但当前 LP Controller 不支持，不能直接发到现有入口并期待成功。采用时另行确认事件字段、版本或 `updatedAt`、重复/乱序规则，并由 LP 补充处理。状态推送不能代替周期对账。

## 7. 仅在逐单申请或共享库存时追加

如果 PC 无法提供可由 LP 独立分配的资源池，需要额外协议，不能只放开当前采购入口：

- 原子申请/锁定：资源范围、租期、价格、幂等键和保留时限。
- 查询结果：用幂等键或双方订单号查询，解决“请求超时但 PC 已执行”的情况。
- 确认/取消/释放：说明是否存在确认阶段、何时生效、是否收费及重复调用结果。
- 状态与扣费：明确各状态、成本记录和失败补偿；未确认结果时不能再次采购或向客户报成功。

本节是条件需求，未确认采用前不计入批量供号的必需接口。无用户支付接入，不代表可以忽略上游收费和本地余额记账。
