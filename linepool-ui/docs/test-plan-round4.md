## 一、执行规则（必须遵守）

1. **只测试、只记录，不改业务代码。** 发现问题写进文档，由产品负责人决定是否修复。
2. **遵守 `AGENTS.md`**：不运行测试套件（`npm test` 等）；可以运行 typecheck、构建和浏览器 / 接口手工测试。不改 `src/vendor/**`、`public/**`、`upstream-lock.json`。
3. **只动测试数据。** 允许写操作的对象只有第三节表格里列出的账号和号码。其他账号（例如 `settlement-*`、`batch-*`、`agent-review-*`）是其他会话的核验数据，**只读不写**。
4. **改数据库之前先备份**（第五节第 1 项、第六节都会直接改库）：
   ```bash
   cd backend
   node --env-file=.env scripts/backup-local-db.mjs
   ```
   备份文件在 `backend/.local/backups/`，把文件名记进报告。
5. **只连本机。** 数据库是 `127.0.0.1:5433`，接口是 `127.0.0.1:3010`，页面是 `http://127.0.0.1:5178`（要用 127.0.0.1，不要用 localhost）。不得把签名密钥、密码写进文档或输出到聊天里。
6. 每个用例记录：**结果（通过 / 不通过）**；不通过时写现象、位置和截图或接口返回。
7. 测试结束后，按第八节的“数据恢复”把能恢复的数据恢复，恢复不了的写进报告。

## 六、T1 模拟收短信（LP 侧的分发逻辑）

### 背景（已查明）
- 接收入口：`POST /api/webhooks/pingcode`，签名密钥是 `backend/.env` 的 `PINGCODE_WEBHOOK_SECRET`（本地已配置）。
- 签名规则：
  - `X-PingCode-Timestamp`：10 位秒级时间戳，和服务器时间相差不能超过 ±300 秒
  - `X-PingCode-Signature`：`sha256=` + `HMAC_SHA256(secret, timestamp + "." + 原始请求体)` 的十六进制
  - `X-PingCode-Event-Id`：必须和请求体里的 `eventId` 一致
  - `Content-Type: application/json`
  - 代码位置：`backend/src/providers/pingcode-webhook.ts`
- 请求体：
  ```json
  { "eventId": "qa-evt-001", "event": "sms.received", "occurredAt": "<ISO 时间，不能晚于当前 5 分钟>",
    "data": { "messageId": "qa-msg-001", "projectId": "<上游项目 ID>", "numberId": "<上游号码 ID>",
              "phoneNumber": "+1...", "from": "Telegram", "content": "Your code is 123456" } }
  ```
- **匹配规则**（`backend/src/providers/webhook-inbox.ts` 约第 73 行）：只匹配 `provider='pingcode'` 的项目和号码绑定 → `number_allocations`（直销号码），并且短信接收时间要落在分配有效期内。
- **关键限制**：本地所有号码都是演示数据 `pingcode-mock`，没有 `pingcode` 的项目和号码绑定。**不准备数据就推送，结果一定是“未匹配”。**
- 代理库存号码（`agent_number_stock` / `number_holdings`）**根本不在匹配范围内**。

### 准备测试数据（只针对小王自己买的 `+19598119199`）
先按第一节第 4 条备份数据库。然后在一个事务里执行：
1. 插入 `provider_projects`：`provider='pingcode'`，`external_project_id='qa-proj-telegram'`，`platform_id='Telegram'`，`project_name='QA Telegram'`。表上有 `UNIQUE(provider, platform_id)` 约束，所以先确认没有 `pingcode / Telegram` 的记录。
2. 把 `+19598119199` 在 `number_platforms` 中 Telegram 那一行的 `provider` 改为 `pingcode`，`external_project_id` 改为 `qa-proj-telegram`。**先记下原值，用于恢复。**
3. 插入 `provider_resource_bindings`：`provider='pingcode'`，`external_number_id='qa-num-19598119199'`，`number_id=<该号码的 id>`，`external_project_id='qa-proj-telegram'`。

脚本放在会话的 scratchpad 目录，用 `node --env-file=backend/.env` 运行，并且只允许连接 127.0.0.1。

## 七、T2 到期

后台有两个定时任务，每 30 秒运行一次：
- `allocation-expiry.ts`：直销号码到期
- `agent-inventory-expiry.ts`：代理库存号码到期。到期后持有记录变为 `RETIRED`，号码在 `agent_number_stock` 中**回到平台的可分配状态**（`AVAILABLE`），不会回到上级代理

| 编号 | 操作 | 检查点 |
|------|------|--------|
| T2-01 | 把小李持有 `+65815561006` 的 `number_holdings.expires_at` 和对应 `service_entitlements.expires_at` 改为当前时间往后 2 分钟，等待 3 分钟 | ① 小李的库存里，号码状态变为“已结束”；② 号码**回到平台的代理库存池**，而不是回到一级代理（印证 R1 的问题：一级没有拿回剩余的 22 天）；③ 管理员“代理库存 → 号码库存”中出现这个号码，状态为可分配 |
| T2-02 | 把小王自己买的 `+19598119199` 的 `number_allocations.expires_at` 改为 2 分钟后（如果做了 T1，先恢复 T1 的数据，或者在 T1 之后再做这一项） | ① 到期后，小王“我的号码”显示“已过期”；② 到期后推送的短信“未匹配”；③ 号码在后台回到可售还是不可售，记录实际行为；④ 是否有任何“即将到期”的提醒出现过 |
| T2-03 | 让某个号码处于 3 天内到期（改 `expires_at` 为 2 天后） | ① 管理员概览“即将到期的号码”出现它；② 小王“账户设置 → 提醒偏好”显示它；③ 小王首页“号码有效期”是否有提示 |

**改到期时间之前记下原值。** 已经到期的号码无法“恢复到期前的状态”，所以 T2-01、T2-02 只能放在最后做，并在报告中写明。

## 十、已知的预期结论（用来对照）

下面是根据代码推断的结果，执行时请确认或推翻：
- 代理库存号码（客户的、二级代理的）**收不到短信**，因为短信路由只匹配直销号码。这会直接决定客户改造方案 F7 的必要性。
- 二级代理持有的号码到期后，号码回到**平台**的代理库存池，**不会回到一级代理**，所以转交部分时长时剩余的天数确实会作废（R1）。
- 二级代理不能管理下级、不能设下级价格，相关接口返回 403。
