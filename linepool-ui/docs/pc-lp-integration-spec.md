# PC-LP 对接接口与业务流程说明

> 状态：早期业务草案，供了解整体流程。2026-11-02 本次首发的接口确认与联合验收以 [PC → LinePool API 对接清单](./pc-lp-api-checklist.md) 为准：不接用户支付；号码续费和用量已补入清单（A9、A10），供货与占用边界仍需 PC 确认。
>
> 本文保留早期方案讨论；其中 Webhook 字段、签名、响应、补偿方式及支付上线前置条件如与最新清单不同，以清单为准。下文的接口设想不代表 PC 已交付或 LP 已完成实现。
>
> 本文定义 LP 需要的业务结果、数据契约和验收标准，不规定 PC 内部如何实现 Webhook。

## 1. 对接目标

PC 提供项目、号码和短信能力；LP 负责：

- 展示 PC 提供的可用号码；
- 将号码按平台、客户和租期进行销售与分配；
- 接收 PC 推送的短信；
- 根据项目和号码归属，把短信展示给正确客户；
- 记录订单、余额、权益、号码状态和短信流水。

## 2. 双方职责

### LP 负责

1. 定义业务流程和接口契约；
2. 提供 Webhook 接收地址；
3. 保存项目、号码、客户和分配关系；
4. 校验签名、幂等处理和短信归属；
5. 对外提供号码、订单和短信查询；
6. 对异常事件、重复事件和未知号码进行记录。

### PC 负责

1. 在 PC 内部创建和配置 Webhook；
2. 监听项目、号码和短信事件；
3. 按本契约发送请求；
4. 实现 PC 内部的重试、事件组装和发送；
5. 提供项目和号码的查询或同步能力；
6. 确认项目、号码、短信标识的稳定性和唯一性。

LP 不要求 PC 按指定语言、框架或模块实现 Webhook。

## 3. 推荐业务流程

```text
PC 创建项目和号码
    ↓
LP 获取项目及可用号码清单
    ↓
LP 保存 projectId、numberId、号码和平台支持范围
    ↓
客户在 LP 购买号码/平台权益
    ↓
LP 创建本地分配关系：项目 + 号码 + 客户 + 租期
    ↓
PC 收到短信
    ↓
PC 调用 LP Webhook
    ↓
LP 校验签名和 eventId
    ↓
LP 根据 projectId + numberId 查询当前分配关系
    ↓
LP 保存短信并展示给对应客户
```

LP 不应只使用手机号匹配客户。推荐使用：

```text
projectId + numberId
```

手机号用于展示和辅助校验，不能作为唯一归属键，因为号码可能过期、回收或重新分配。

## 4. 项目和号码同步

Webhook 适合通知变化，不适合作为唯一的库存查询方式。PC 至少需要提供以下一种能力：

### 方案 A：查询接口（推荐）

```http
GET /projects
GET /projects/{projectId}/numbers
```

号码记录至少需要：

```json
{
  "projectId": "project_001",
  "numberId": "number_001",
  "phoneNumber": "+12025550100",
  "status": "available",
  "supportedPlatforms": ["telegram", "whatsapp"],
  "availableFrom": "2026-01-01T00:00:00Z",
  "availableUntil": "2026-02-01T00:00:00Z"
}
```

### 方案 B：完整快照 + 变化 Webhook

PC 首次提供完整项目和号码快照，之后通过以下事件通知变化：

```text
project.created
number.created
number.status_changed
number.released
number.expired
```

无论采用哪种方案，LP 都需要能够定期对账，避免因为 Webhook 丢失导致库存不一致。

## 5. LP Webhook 接口

当前项目已有接收入口：

```http
POST /api/webhooks/pingcode
```

### 请求示例

```json
{
  "eventId": "evt_123456",
  "event": "sms.received",
  "occurredAt": "2026-01-01T12:00:00Z",
  "data": {
    "projectId": "project_001",
    "numberId": "number_001",
    "phoneNumber": "+12025550100",
    "messageId": "msg_123456",
    "from": "+8613800138000",
    "content": "Your code is 123456"
  }
}
```

### 必填字段

| 字段 | 说明 |
|---|---|
| `eventId` | Webhook 事件唯一 ID，用于幂等 |
| `event` | 事件类型，例如 `sms.received` |
| `occurredAt` | PC 产生事件的时间 |
| `projectId` | 项目或平台服务的稳定 ID |
| `numberId` | PC 内部号码稳定 ID |
| `phoneNumber` | E.164 格式号码 |
| `messageId` | 短信唯一 ID |
| `from` | 短信发送方 |
| `content` | 短信正文 |

### 签名和鉴权

PC 必须提供签名或等价鉴权机制。推荐：

```text
timestamp + request body
```

使用共享密钥生成 HMAC 签名，并防止重放攻击。签名字段名称和算法由双方最终确认。

### LP 响应

| 状态码 | 含义 | PC 是否重试 |
|---|---|---|
| `200` | 已成功接收，或已幂等处理 | 否 |
| `400` | 请求格式错误 | 否，需人工处理 |
| `401/403` | 签名或鉴权失败 | 否，需修复配置 |
| `404` | 项目或号码不存在 | 需双方确认是否重试 |
| `409` | 事件重复或状态冲突 | 通常否 |
| `500` | LP 暂时不可用 | 是 |

PC 应至少对 `5xx` 进行重试，并使用指数退避。最终失败的事件必须保留，供人工或补偿接口处理。

## 6. 短信正文的处理方式

推荐方案：

- Webhook 直接携带短信正文；
- 现有短信查询 API 用于历史查询、补偿和对账；
- LP 不需要在每条实时短信到达时再次请求 PC。

如果 PC 只能在 Webhook 中提供 `messageId`，则必须同时提供可靠的短信查询接口，且 LP 能够根据 `messageId` 获取完整正文。

PC 内部到底从哪个服务读取短信正文，由 PC 负责人决定；但对 LP 而言，最终必须满足：

> LP 能够在收到事件后可靠地获得完整短信正文，并且不会因为一次接口失败而永久丢失短信。

## 7. 幂等、顺序和异常规则

### 幂等

LP 使用 `eventId` 和 `messageId` 防止重复入库。PC 重试同一个事件时，LP 应返回 `200`，不能重复创建短信。

### 顺序

PC 不能假设网络一定按顺序送达。LP 需要根据 `occurredAt` 和本地状态处理乱序事件。

### 未知项目或号码

如果 Webhook 中的 `projectId + numberId` 在 LP 不存在：

1. 保存原始事件；
2. 不向任何客户展示；
3. 返回双方约定的状态码；
4. 通过同步或人工流程补偿。

### 已过期或已回收号码

短信仍应保存，但不能展示给当前新客户，避免旧号码的短信泄露给新归属人。

## 8. 供货和销售模式

双方必须在以下两种模式中确认一种。

### 批量供号

1. PC 批量提供号码；
2. LP 自己销售和分配；
3. PC 只负责号码状态和短信通知。

优点是流程简单、实时依赖少。当前 LP 更适合该模式。

### 逐单申请

1. 客户下单；
2. LP 向 PC 申请号码；
3. PC 锁定或分配号码；
4. LP 成功后创建权益。

该模式必须另外定义锁定、超时、取消、失败和释放接口。

## 9. PC 必须确认的问题

1. 是否提供项目列表接口？
2. 是否提供项目下号码列表接口？
3. `projectId` 是否稳定且唯一？
4. `numberId` 是否稳定且唯一？
5. 短信 Webhook 是否包含 `projectId` 和 `numberId`？
6. 短信正文是否直接放在 Webhook 中？
7. 是否支持签名、重试和失败事件保存？
8. 号码是否允许跨平台同时使用？
9. 同一平台的号码是否可能被重复分配？
10. 号码过期、回收、下线时如何通知？
11. 采用批量供号还是逐单申请？
12. 是否提供测试项目、测试号码和测试短信？

## 10. 验收标准

接口联调完成必须至少通过以下场景：

- 获取项目列表；
- 获取项目下可用号码；
- LP 成功保存号码状态；
- PC 发送一条真实格式的短信 Webhook；
- LP 正确将短信归属到项目、号码和客户；
- 重复发送同一事件不会产生重复短信；
- 非法签名被拒绝；
- Webhook 暂时失败后可以重试；
- 未知号码不会展示给错误客户；
- 号码回收后，旧短信不会泄露给新客户；
- 可以通过短信查询接口补偿缺失事件。

## 12. 最终判断

如果 PC 只提供短信 Webhook，而不提供项目/号码同步或快照能力，LP 不能稳定完成库存和归属管理。

如果 PC 能提供：

1. 项目和号码清单；
2. 带 `projectId + numberId + messageId + content` 的短信 Webhook；
3. 签名、重试和状态变化通知；
4. 短信补偿查询接口；

那么 LP 可以完成正式联调。联调通过后，再补支付、结算和生产部署能力，才适合正式商业使用。
