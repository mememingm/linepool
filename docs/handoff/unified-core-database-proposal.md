## 0. 批准结论与删减（优先于下文）

### 2026-11-06 实施接收修订（优先于历史条目）

- 同一schema分别部署到LP、ONCE数据库；`app.site_id`作为持久数据库标识，应用和worker启动前只读核对，迁移/导入执行前也核对。标识配置属于R5授权步骤，不由启动代码自动写入。
- 现有031/032不改写；旧worktree候选033–036不执行，新链037–041自洽承接。037分别约束PLATFORM和WHOLE期间，不采用旧跨类型scope/numrange设计；038保留严格客户SMS身份；039保留自营钱包/充值/退款历史/导入事实；040先保存旧分配快照并核对归属，再移除废弃物理分配列。
- 041复用`upstream_accounts`承载连接所有权、授权状态、令牌领取和轮询状态；每站一个运营自营连接、每代理一个自有连接。`historical_only`来源账户仅保留旧provider/account事实，排除于运营连接唯一性与worker；不得把旧demo或其他PC来源重标成当前Mock账户。
- 代理取码复用`provider_message_receipts`的载荷、去重和冲突证据，以`connection_id/owner_agent_id/number_id`固定身份，`CONNECTION_IMPORTED`禁止绑定客户message/allocation；自营消息继续要求真实使用期间。连接归属不可转给另一主体。
- 外部ID主键继续保留；项目的旧全局`UNIQUE(provider,platform_id)`改为账户范围，允许不同代理声明各自项目。号码来源缺失保留历史并停止新操作；失败或不完整同步不作全量缺失判断。
- 代理套餐是独立配置，不产生自营订单、冻结、批发扣款或结算。历史代理币种账和客户数据保留，不启用新分销写入。近期仍不做现金退款、支付渠道三表或积分来源批次。
- 本节登记代码接收决定，未执行数据库迁移或业务验收；进度与执行证据见总文档RUN-20261106-llinepool-16872-03及后续记录。

### 历史批准条目


**照原方案执行：**
- 保留并扩展 `number_allocations`，增加 `PLATFORM` / `WHOLE_NUMBER` 类型，作为唯一的使用期间和收信归属依据。代理的持有和授权表保持现状；自营用户不经过代理持有链。
- 号码的门店由所属 PC 账户推出，号码上不另存门店。区分销售门店和资源门店。
- 保留 ONCE 的租约生命周期，包括续租和到期保留（`EXPIRED_HELD`）。到期和可售分开判断。
- 代理结算保留币种金额。自营积分价和代理批发价各自定价。
- 订单和履约规则：幂等、结果不确定时保留冻结和预留、在数据库锁之外调用上游。

**删减或推迟：**
1. **上游表的唯一键和外键不按账户重写**（删减第 2 节"必须一起调整的内容"中的大部分）。两个 PC 账户在同一个 PC 系统里，号码 ID、短信 ID 在全平台本来就唯一。只在需要路由或筛选的地方补账户字段：号码、PC 项目、Webhook 收件箱的路由记录。外部 ID 是否全平台唯一，需要向 PC 确认一次；如果确实只在账户内唯一，再单独改键。
2. **支付相关的三张表推迟**（第 5 节第 3 段）：`PaymentAttempt`、`PaymentReceipt`、`PaymentEvent` 等支付渠道选定后再设计。S4 只迁充值订单和退款订单，使用 Mock 支付。
3. **积分批次和分摊视现金退款决定**（第 5 节）：近期做现金退款，就按本方案保留；不做，S3 先只实现账户、冻结、流水。S3 设计说明开头先请用户确认。
4. **S2 的范围随第 1 条缩小**（第 9 节第 1 条）：不覆盖"所有账户相关调用链"，只改号码同步和 Webhook 路由中写入或读取账户的地方。

**S8 补充：** 电话站需要新增 `calls`、`rate_cards`，以及钱包的"部分扣除、释放剩余"操作；到 S8 时再出详细设计。

## 1. 方案结论

以 LinePool 现有核心为基础，迁入 ONCE 的积分钱包、租约及收发短信能力，补齐多 PC 账户隔离。

保留 `number_allocations` 作为统一的使用时间和短信归属依据。代理继续保留必要的分销记录，ONCE 保留必要的租约生命周期记录。自营用户不经过代理持有链。

本方案优先复用已经工作的模型，不以减少表数量为目标，也不为统一表名重写业务。

### 已有业务边界

- 一个核心后端，基于 LinePool 的 NestJS 后端。
- LinePool、ONCE、电话站为不同前端，自营账号和积分钱包共用。
- LinePool 和 ONCE 使用不同 PC 账户，号码不跨门店调配。
- 电话站作为独立门店，不接入 LinePool 前端。
- 白标放在 S7：代理商户账号独立，自营三个门店继续共用账号。
- 当前阶段仅接 Mock，不连接真实 PC、SIP 或支付渠道。

### 本方案建议的调整

- 不退役 `number_allocations`；扩展它承载整号使用权。
- 不要求所有自营用户创建 `number_holdings`、`service_entitlements`。
- 保留代理币种结算，不强制改成积分。
- 保留积分批次和分摊，以承接现有充值退款能力。
- 不提前实施白标，不新增通用结算引擎、工作流引擎或库存池管理层。

以上属于待审阅建议；尤其代理结算单位和号码模型的调整，不应被执行者误认为已经批准。

## 2. 门店与上游账户

### 表结构职责

| 表 | 职责 | 处理方式 |
|---|---|---|
| `storefronts` | 销售门店及产品类型 | 新增，不把门店 ID 限死为固定几个值 |
| `upstream_accounts` | 上游账户身份、资源门店、状态 | 新增；密钥保留在环境配置中 |
| `phone_numbers` | 物理号码及资源状态 | 增加明确的上游账户关联 |
| `provider_resource_bindings` | 外部号码与本地号码的映射 | 改为按上游账户识别资源 |
| `provider_projects` | 上游项目与本地平台映射 | 改为按上游账户识别项目 |
| `provider_message_receipts`、`provider_event_receipts` | 收件箱及消息、事件去重 | 补齐账户范围 |
| `provider_sync_tasks`、`provider_sync_conflicts` | 同步执行与冲突记录 | 补齐账户范围及关联约束 |

### 归属规则

1. `upstream_accounts` 以 `(provider, external_account_id)` 唯一标识上游账户。
2. 号码通过 `upstream_account_id` 确定来源；资源门店从账户取得，不再在号码上独立维护另一份可修改的门店归属。
3. 模拟资源同样归属明确的 Mock 账户，不能用空账户表示所有本地资源。
4. 订单记录销售门店。销售门店与号码资源门店是不同概念：代理白标站可以销售平台分配给它的号码，不要求每个白标站拥有 PC 账户。
5. 已能通过关联可靠确定账户的记录，不机械地重复增加账户字段；但相关外键必须保证关联属于同一账户。

### 必须一起调整的内容

外部资源、项目、消息和事件的唯一键，相关外键、查询、冲突处理、幂等锁、同步任务领取，以及 Webhook 路由，均按账户区分。

例如，消息按“上游账户 ID＋外部消息 ID”识别。两个账户使用相同外部消息 ID，必须各自处理；同一账户重复投递同一消息，不能重复入库。

账户上下文来自可信的上游连接配置和验证结果，不由调用方随意指定门店来决定短信归属。

S2 的改动范围需要覆盖现有账户相关调用链；只在号码表加字段、只修改 Mock 入参不足以完成隔离。仍然不连接真实上游。

## 3. 号码、代理持有与使用权

### 保留的职责分工

| 表 | 职责 |
|---|---|
| `phone_numbers` | 物理号码、上游来源、资源状态与资源有效期 |
| `number_platforms` | LinePool 的号码＋平台可售库存 |
| `number_allocations` | 用户实际使用号码的有效期间；统一收信归属依据 |
| `number_holdings` | 代理进货、转让、分配的持有历史及成本 |
| `service_entitlements` | 现有代理授权记录，继续通过已有机制关联使用权 |
| `leases` | ONCE 租约身份、续租关系、保留和释放状态 |

### 为什么保留 `number_allocations`

现有库存占用、收信路由、历史短信归属和部分业务查询已依赖这张表。030 迁移已经将代理授权连接到 `number_allocations`，并非两套完全独立的收信系统。

整体迁往 `service_entitlements` 会同时改动大量调用方和数据库保护机制，但不会天然增加业务能力。因此本次扩展现有使用权表，不迁走它。

代理授权和使用权仍有部分字段重复，这是保留现有代理流程的取舍。它们继续受已有数据库联动约束，不作为两套可独立修改的收信归属来源。自营流程不再增加这层重复。

### 使用权类型

`number_allocations` 增加明确类型：

- `PLATFORM`：按平台使用，必须有 `platform_id`。
- `WHOLE_NUMBER`：整号使用，`platform_id` 为空，直接关联物理号码。

约束与处理规则：

1. 按平台使用权，按“号码＋平台＋有效时间区间”禁止重叠。
2. 整号使用权，按“号码＋有效时间区间”禁止重叠；不能依赖包含空平台字段的旧约束实现独占。
3. 类型必须符合资源门店的产品规则。LinePool 按平台，ONCE 整号；上游账户和资源门店关联不得被随意修改以绕过分池规则。
4. 整号使用权不伪造 `number_platforms` 记录；原有强制平台关联的外键和触发器需要按类型调整。
5. 保留用户、号码、订单的一致性校验和历史归属保护。涉及可空平台字段的复合外键，需要另行保证整号记录的身份一致性，不能因空值跳过必要校验。
6. 服务期间不得超过已确认的上游资源可用期限。
7. 自营订单直接产生使用权；代理继续使用现有分配、转让和授权机制。

### 收信规则

- `sms_messages` 继续关联 `allocation_id`，不迁往另一张使用权表。
- LinePool 按上游账户、号码、可信平台映射和消息发生时间匹配使用权。
- ONCE 按上游账户、号码和消息发生时间匹配整号使用权，不要求消息携带平台项目才能归属。
- 采用半开区间 `[开始时间, 结束时间)`，提前释放时以实际释放时间截断。
- 迟到消息按历史有效期间归属，不按 Webhook 到达时的当前持有人归属。
- 找不到唯一有效使用权的消息保留在收件箱，不交给当前用户。
- 转让、释放及重新出租，不改变已入库短信的历史归属。

## 4. ONCE 租约与号码释放

### 租约不是第三套收信归属

保留 `leases` 是为了承接稳定的租约 ID、续租关系和到期保留行为。一个租约关联多个实际使用期间，短信访问统一依据 `number_allocations`。

租约与使用期间的用户、号码必须一致。实际服务时间以使用期间为准；租约展示的起止时间由关联期间取得，不维护另一套可独立修改的服务期限。每次购买的期限和价格保存在订单快照中。

### 续租

- 续租订单成功后追加有效使用期间，不覆写历史期间。
- 未到期续租，新期间衔接原结束时间。
- 到期后重新续租，新期间从重新生效时开始。
- 中间停用时间不自动补成已购买的使用期间；这是本方案明确推荐的归属规则。
- 同一租约 ID 下展示各期间的短信，保持 ONCE 的租约操作入口。

### 到期与可售分开判断

ONCE 现有行为是到期后进入 `EXPIRED_HELD`，并非立即重新上架。本次保留该能力：

1. 使用期间到期后，停止产生新的使用权限。
2. 租约进入保留状态，号码继续禁止出售。
3. 释放／冷却条件未配置时，不自行释放。
4. 满足已配置条件后，完成租约释放，再恢复号码可售。

因此整号库存可售必须同时检查：资源状态、有效使用权、待处理订单预留、租约保留和冷却状态。没有有效使用权不等于可以出售。

LinePool 原到期任务应明确只处理其对应类型，不能误释放 ONCE 保留号码。

## 5. 自营积分钱包

### 目标表

| 表 | 职责 |
|---|---|
| `point_accounts` | 可用积分、冻结积分、账户状态 |
| `point_ledger` | 只追加的积分变动及变动后余额 |
| `point_lots` | 充值、补偿等积分来源 |
| `point_reservations` | 业务冻结及处理状态 |
| `point_allocations` | 一次冻结使用了哪些积分批次 |
| `recharge_orders` | 充值订单 |
| `refund_orders` | 现金退款订单 |

沿用 ONCE 已有语义，按核心数据库命名及访问方式实现，不再另建同义的 `point_holds`。`point_allocations` 是积分分摊，与号码使用权无关。

充值、退款所需的支付尝试、付款凭证和回调去重记录同样必须迁入或映射到核心已有记录；上表不是完整支付模块表清单，不能据此省略现有支付能力。

### 资金规则

- LinePool、ONCE 自营消费共用一个用户积分账户。
- 账户、批次、冻结和流水在同一数据库事务中更新。
- 余额及冻结额不得为负；账户汇总与批次明细一致。
- 使用业务类型和业务 ID 保证幂等；同一个幂等请求的参数发生变化时应拒绝。
- 消费退积分关联原消费，累计退回不超过原实际扣款，并恢复相应积分来源。
- 充值退现金关联原充值及有效付款凭证，只退符合规则的未消费余额。
- 保留付费积分和补偿积分的区别，不将补偿积分作为现金退款来源。

保留批次与分摊是为了承接 ONCE 已有退款能力，不是为了新增多币种兑换或复杂促销引擎。

### 迁移原则

- 将全部自营积分读写迁入统一钱包，停用 `users.points_balance`，不保留双写。
- 保留历史流水和业务引用，明确迁入余额的来源及对账起点，不伪造缺失的历史记录。
- 来源不明的旧积分不得伪造成可退现金的充值。
- 迁移范围包括下单、失败退分、充值、后台调整及仍有效的历史业务读取。
- 当前 LinePool 短期接码已禁用的续费功能不因数据库合并而重新开启；ONCE 的续租能力独立承接。

### 电话站扩展位置

ONCE 当前冻结处理支持全额扣除或全额释放。电话站需要部分扣除并释放剩余冻结，在 S8 扩展同一个钱包操作。

S3 不提前实现通话计费引擎，也不声称现有钱包已经完整支持语音结算。

## 6. 代理结算与价格

建议保留现有 `balance_accounts`、`balance_ledger`、`tx_orders`、`tx_order_items`、`price_rules`。

- 保留币种和最小货币单位金额，不强制改为积分。
- 保留已有客户金额账户；本次不迁移代理客户的收款方式。
- 代理当前只记销售金额的零售流程继续保持，不能在合并时自动改成扣客户积分。
- 已经在进货时扣除的代理成本，不能在客户使用时重复扣除。
- 批发金额价、自营积分价可以独立定价，不要求固定比例联动。
- 只有实际发生兑换时，才需要记录兑换规则和交易快照；当前不新建兑换系统。

本阶段“一套积分钱包”指自营消费渠道统一，不代表所有资金都必须合并成同一种单位。

## 7. 订单与履约

### 订单边界

- C 端继续使用 `orders`，增加产品类型。
- LinePool 订单关联其商品；ONCE 订单关联 `lease_plans`。
- 调整旧的商品外键及非空约束，并用产品类型约束对应字段，避免为了通过旧约束伪造平台商品。
- 订单保存成交时的价格、期限、必要的币种／积分信息及版本快照。
- 订单关联资金冻结记录，以及租约或交付的使用权。
- 代理继续使用 `tx_orders / tx_order_items`，不强制合并成通用订单表。

### 履约规则

复用现有订单处理能力，承接 ONCE 的处理中、成功、失败、结果不确定等语义，不新增通用工作流引擎。

1. 创建业务订单，冻结积分并预留资源。
2. 在数据库锁之外执行上游操作；当前为 Mock。
3. 明确成功后，在同一数据库事务中完成扣款、使用权生效及订单完成。
4. 明确失败后，释放该业务对应的积分冻结和资源预留。
5. 结果不确定时保留冻结和预留，按原业务标识查询结果，不重复购买。

发短信同样保留幂等、处理状态和结果不确定时的核对能力。ONCE 的充值、退款、管理接口及 Webhook 收件箱能力均需有明确迁入位置，不仅迁表名。
