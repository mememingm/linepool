## 1. 一句话

**一个核心后端，多个店面。** 平台自营（C 端）被当作一个特殊的商户，和 B 端代理用同一套模型。LinePool（接码）、ONCE（号码）以及以后的电话站，都只是挂在某个商户下面的店面。

## 2. 总体架构

```
  店面（前端）
  ┌──────────────┬──────────────┬──────────────┬───────────────────┬────────────────┐
  │ LinePool 接码 │ ONCE 号码     │ 电话站（以后）│ 代理白标站（以后）  │ 开放 API（以后） │
  └──────┬───────┴──────┬───────┴──────┬───────┴─────────┬─────────┴───────┬────────┘
         └──────────────┴──────────────┼─────────────────┴─────────────────┘
                              ┌────────▼─────────────────────────────────────────┐
                              │ 共用核心（一个后端，基于现有 LinePool 后端）          │
                              │  商户与店面 · 账号 · 钱包 · 定价 · 号码库存 · 订单      │
                              │  风控 · 运营后台 · 代理后台 · 审计                     │
                              ├──────────────────────────────────────────────────┤
                              │ 能力模块：收短信 · 发短信 · 彩信 · 验证码识别 · 语音    │
                              ├──────────────────────────────────────────────────┤
                              │ 上游接入层：PC 适配器 · Webhook 收件箱 · 同步任务       │
                              └────────┬─────────────────────────────────────────┘
                                       ▼
                        PC（号码、短信）· 同事的 SIP（电话）· T-Mobile SIM 卡
```

## 3. 商户模型：C 端和 B 端怎么共存

```
平台（我们）：持有全部号码、对接上游、给代理定批发价
├─ 商户：平台自营（PLATFORM）
│   ├─ 店面：LinePool 接码 ┐
│   ├─ 店面：ONCE 号码     ├ 共用同一批 C 端账号和余额
│   └─ 店面：电话站        ┘
├─ 商户：代理甲（AGENT）── 店面：甲的白标站 / 甲的 API Key ── 甲的客户
│   └─ 商户：下级代理（AGENT，上级是甲）── 他的客户
└─ 商户：代理乙（AGENT）── 只用开放 API ── 乙的客户
```

| 规则 | 平台自营（C 端） | 代理（B 端） |
|---|---|---|
| 客户归属 | 平台 | 代理；客户只看到代理的品牌 |
| 账号范围 | 同一套账号（2026-11-04 定：不做白标，代理的客户也登录 LinePool 网站，账号上记着属于哪个代理） | 同左 |
| 价格 | 平台零售价 | 平台给代理批发价，代理自己给客户定零售价 |
| 扣费 | 只扣客户 | 客户按零售价扣代理侧余额；代理按批发价扣平台侧余额 |
| 号码 | 平台号码池 | 平台划给代理的库存（以后也可以是代理自带的 PC 号码） |
| 品牌 | LinePool / ONCE 的品牌 | 同左，不做白标 |


- 运营后台以 LinePool 的 admin 为基础，补上 ONCE 后台有、LinePool 没有的页面。
- 代理后台沿用 LinePool 的 `src/linepool/agent`。

### 关键规则：号码按 PC 账户划分给门店（2026-11-04 已定）

LinePool 按平台卖（同一个号码，Telegram 卖给甲、WhatsApp 卖给乙），ONCE 整号出租。为了不让两种卖法抢同一个号码，在 PC 上分开开账户：

- PC 账户 A：只给 LinePool（接码）。
- PC 账户 B：只给 ONCE（号码）。

对应到核心：
- 每个 PC 账户是一条"上游连接"，绑定一个门店（产品）。从这条连接同步来的号码，只能在对应门店售卖。
- 两种模式天然隔离，不需要跨模式的互斥规则。每个门店内部的占用规则保持不变：LinePool 按平台分配，ONCE 按租约独占。
- 每个 PC 账户各配一个收信 Webhook，地址按连接区分，归属一目了然。
- 代价：号码不能在两个门店之间随意调配，要调配只能在 PC 上转移账户。
- 代理（B 端）卖接码时，用的是 LinePool 账户下的库存。

### 语音只给 ONCE

语音能力以后只在 ONCE（整号出租）上开放，LinePool 不接。核心里，语音是按门店开关的能力模块。

## 7. 一笔代理交易的例子

代理甲的客户 C 买一个 30 天的号码：

1. 按店面域名识别出商户是甲，C 是甲的客户。
2. 按 AGENT_RETAIL 价格扣 C 的余额（甲这边的账）。
3. 按 WHOLESALE 价格扣甲在平台的余额（平台这边的账）；如果甲有上级代理，逐级结算。
4. 持有链记录：平台 → 甲 → C；每一层都记成本和售价。
5. 号码收到短信后，按归属规则投递给 C，同时通过 Webhook 推给甲（如果甲用的是 API）。

如果是平台自营客户购买，第 3 步不存在，只扣一笔。

## 10. 并发量变大怎么办

"共用一个后端"指的是**一套代码、一个数据库**，不是"只有一台服务器"。扩容按下面的顺序来，前面的做完了再做后面的：

| 顺序 | 做法 | 解决什么 |
|---|---|---|
| 1 | 后端保持无状态（会话存在数据库里，现在已经是这样），在负载均衡后面开多个实例 | 接口请求量大 |
| 2 | 同一份代码按角色分开部署：`api`（处理网页请求）、`worker`（同步上游、处理 Webhook、发短信）、`open-api`（只给代理调用） | 后台任务拖慢网页；大代理的 API 流量影响 C 端用户 |
| 3 | 每个商户、每把 API Key 单独限流 | 单个客户把系统打满 |
| 4 | Postgres 加连接池（PgBouncer）、只读副本；短信表按月分区 | 数据库成为瓶颈 |
| 5 | 热点数据加缓存（Redis），比如价格、库存数量 | 重复查询太多 |
| 6 | 真正的瓶颈模块（例如收短信入库）拆成独立服务 | 单个模块量级远超其他模块 |

实际上，最先碰到的上限通常是上游：PC 的接口频率限制和号码数量，而不是我们自己的后端。每个上游连接都要做排队和限速。
